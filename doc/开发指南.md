# BubblePilot 开发指南

本文面向修改 BubblePilot 服务、Web、适配器、工作流节点和部署配置的开发者。当前仓库处于文档和架构阶段，具体语言与框架在实现第一条垂直切片时通过独立 PR 固化；模块边界、数据合同和验证要求先于框架细节。

## 1. 开发原则

- 先从需求编号和验收标准开始，再创建实现分支。
- 以模块化单体实现消息接入、归档、匹配、编排和 Web API。
- 外部依赖通过适配器隔离；节点通过注册表扩展。
- 数据库迁移只追加，不修改已发布迁移。
- Schema、环境变量、认证和数据保留策略变化必须同步更新文档和测试。

## 2. 本地环境

实现阶段至少需要：

- Git；
- Docker 和 Docker Compose；
- 项目选定的后端运行时和包管理器；
- 项目选定的 Web 运行时和包管理器；
- 可访问的测试数据库；
- BlueBubbles 测试实例或脱敏的适配器 Fixture。

真实 BlueBubbles 令牌、AI Key 和聊天内容不得写入仓库。开发环境使用 `.env.local` 或外部 Secret，并确保已被 `.gitignore` 忽略。

## 3. 建议的实现顺序

1. 定义 `MessageEnvelope`、Webhook 入站合同和幂等约束。
2. 实现消息归档和监听范围。
3. 实现触发器匹配和执行状态机。
4. 实现节点注册表和基础节点。
5. 实现 BlueBubbles 回复适配器。
6. 实现 AI Provider 和 AI 节点。
7. 实现 Web 登录、搜索、配置和执行详情。

每一步都应该能独立启动、测试和回滚。

## 4. 验证要求

提交前至少运行：

```bash
docker compose config
```

以及项目实现所提供的：

```text
后端格式化和静态检查
后端单元/集成测试
Web 单元测试和生产构建
数据库迁移校验
工作流 Schema 校验
适配器合同测试
```

如果某个命令尚未建立，应在对应 PR 中补上，而不是在文档里虚构命令。

## 5. 测试边界

- 消息入站：字段映射、签名、重复事件和未知事件。
- 归档：监听范围、唯一约束和敏感字段访问。
- 编排器：顺序、分支、超时、重试、取消和版本锁定。
- 节点：输入校验、输出 Schema、失败分类和幂等。
- AI：超时、限流、输出长度、敏感信息和供应商错误。
- Web：认证、二次验证、越权搜索和审计。
- 部署：Compose 配置、健康检查、备份恢复和升级迁移。

## 6. 数据库和配置变更

- 生产数据模型变更必须新增迁移文件。
- 不把生产消息导出作为测试 Fixture。
- 新环境变量必须记录用途、是否必填、默认值、敏感性和变更影响。
- 删除或重命名配置时提供兼容窗口或迁移说明。

## 7. 日志和调试

每次入站和执行使用 `correlationId`。普通日志记录事件类型、实体 ID、状态、耗时和错误码；不记录完整消息正文、令牌、提示词中的密钥或 AI 原始响应，除非经过显式脱敏并由调试配置控制。
