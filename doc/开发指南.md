# BubblePilot 开发指南

本文面向修改 BubblePilot 服务、适配器、数据存储、工作流节点和部署配置的开发者。当前后端已固化为 Node.js/TypeScript 模块化单体，后续模块必须遵守已有领域合同和依赖方向。

## 1. 技术基线

| 项目 | 选择 |
| --- | --- |
| 运行时 | Node.js 22 或更高版本 |
| 语言 | TypeScript 5，ESM 与严格类型检查 |
| 包管理器 | pnpm 11，版本由 `packageManager` 固定 |
| HTTP | Fastify 5 |
| 数据库 | PostgreSQL 16 |
| 校验 | Zod 与 JSON Schema |
| 测试 | Vitest、Fastify `inject` 和 PostgreSQL 集成测试 |

应用入口、配置和组装位于 `app/`；领域模块位于 `modules/`；供应商 Payload 只允许出现在 `modules/integrations/` 和对应契约中。

完整选型理由、替代方案和重评条件见[技术选型](技术选型.md)。依赖补丁版本以 `pnpm-lock.yaml` 为准，不在文档中重复固定。

## 2. 开发原则

- 先从需求编号和验收标准开始，再创建实现分支。
- 以模块化单体实现消息接入、归档、匹配、编排和 Web API。
- 外部依赖通过适配器隔离；节点通过注册表扩展。
- 数据库迁移只追加，不修改已合并的迁移。
- Schema、环境变量、认证和数据保留策略变化必须同步更新文档和测试。
- 真实 BlueBubbles 令牌、聊天正文和生产数据不能作为 Fixture。

## 3. 本地环境

需要安装：

- Git；
- Node.js 22+ 与 Corepack；
- Docker 和 Docker Compose；
- BlueBubbles 测试实例，或仓库内的虚构适配器 Fixture。

首次安装：

```bash
corepack enable
pnpm install
cp .env.example .env.local
```

本机直接运行时，把 `.env.local` 的 `DATABASE_URL` 主机从 Compose 服务名 `postgres` 改成 `127.0.0.1`，并替换所有 `CHANGE_ME`。随后执行：

登录密码和敏感操作密码只保存 scrypt 哈希。分别选择两个不同密码，通过标准输入生成哈希，再把输出以单引号包裹后写入 `.env.local`：

```bash
read -rs "BUBBLEPILOT_PLAIN_PASSWORD?Password: "
printf '%s' "$BUBBLEPILOT_PLAIN_PASSWORD" | pnpm auth:hash
unset BUBBLEPILOT_PLAIN_PASSWORD
```

不要把明文密码作为命令行参数，以免进入 Shell 历史或进程列表。

随后执行：

```bash
pnpm db:migrate:local
pnpm dev:local
```

应用默认监听 `http://127.0.0.1:8080`；`GET /health/live` 检查进程，`GET /health/ready` 检查数据库。

## 4. 验证命令

提交前运行：

```bash
pnpm verify
docker compose config
```

`pnpm verify` 依次执行：

```text
Prettier 格式检查
ESLint 静态检查
TypeScript 类型检查
Vitest 单元与 API 测试
Shell 运维脚本语法检查
OpenAPI 路由、唯一 operationId、路径参数、引用与环境变量配置契约检查
Markdown 本地链接检查
TypeScript 生产构建
```

设置 `TEST_DATABASE_URL` 后，测试套件会额外运行 PostgreSQL 仓储集成测试。CI 会先执行迁移，再在 PostgreSQL 16 上验证消息事务、唯一约束、管理会话、受控导出的冻结快照和所有者隔离。

主 CI 在 PR、`main` 和版本 Tag 上继续试构建生产镜像；只有 `main` 历史上的 `vX.Y.Z` Tag 会推送正式镜像。`Publish Dev Image` 是独立手动工作流，验证通过后发布 `dev` 和 `sha-<commit>`，详见[版本与发布规范](版本与发布规范.md)。

## 5. 数据库迁移

迁移文件位于 `migrations/`，按文件名升序执行；`schema_migrations` 保存已执行版本，迁移器使用 PostgreSQL advisory lock 防止多个实例并发迁移。

规则：

- 每个生产数据模型变化新增一个 `.sql` 文件；
- 不修改已合并或已发布的迁移；
- 迁移与对应代码、契约、回归测试在同一个 PR；
- 应用镜像启动时先执行迁移，失败则不启动服务。

## 6. 测试边界

- 消息入站：字段映射、共享密钥、请求大小、重复事件和未知事件。
- 归档：监听范围、数据库唯一约束、事务原子性和敏感字段访问。
- 编排器：顺序、分支、超时、重试、取消和版本锁定。
- 节点：输入校验、输出 Schema、失败分类和幂等。
- AI：超时、限流、输出长度、敏感信息和供应商错误。
- 可靠性：API/Webhook 限流、执行并发与等待队列边界、死信人工恢复、未知出站禁止重发、消息内容保留和运行状态告警。
- Web：认证、二次验证、越权搜索和审计。
- 导出：已监听聊天限制、31 天/记录数/大小边界、冻结快照、所有者隔离、短时过期、撤销和敏感字段排除。
- 部署：Compose 配置、健康检查、备份恢复和升级迁移。

PostgreSQL 集成测试还验证人工恢复从数据库重建锁定消息与 Workflow Version，并生成关联而不覆盖原执行的新记录，AI Provider Attempt 的诊断字段可在迁移后完整读回，以及消息内容清理在最终自动化判定后执行并原子写入审计。相关用例要求先运行最新迁移（当前至 `0016_ai_attempt_diagnostics.sql`）。

## 7. 日志和调试

每次请求生成 UUID 格式的 `correlationId`。普通日志只记录事件键、实体 ID、状态和错误码，不记录完整消息正文、Webhook 查询密钥、API Token 或原始 Payload。

AI Provider Attempt 额外记录可关联但不含正文的诊断：客户端请求 ID、供应商请求 ID、HTTP 状态、请求/响应哈希、消息数量、字符数、响应字节数、`finish_reason`、可见输出/推理字符数和 Token/缓存计数。排查 `AI_PROVIDER_EMPTY_OUTPUT` 或 `AI_PROVIDER_INVALID_RESPONSE` 时，先在执行详情按 `executionId → nodeId → round/sequence` 查看所有 Attempt，再用供应商请求 ID、状态、响应大小和哈希判断是否是供应商空响应、协议不兼容或本地解析问题；不要把完整 Prompt 或聊天正文写入日志。缓存优化也必须以 `cachedPromptTokens`、`cacheWritePromptTokens` 和 `cacheMissPromptTokens` 的连续观测为依据。

AI 节点的请求顺序应保持稳定前缀在前、动态上下文在后：系统规则和任务说明放在前部，聊天历史与当前消息分别放在 `<chat_history>`、`<current_input>` 段落。固定工作流 Prompt 不要混入时间戳或当前消息；连续两个 AI 节点重复发送同一段历史会增加 Token 消耗，应优先合并为一个生成节点或让后续节点只接收上游摘要。

BlueBubbles 本身只向配置 URL 发送 `{ type, data }`，不提供内建签名头。应用因此兼容 `token` 查询参数，但关闭框架默认请求日志，避免 URL 查询密钥进入日志；支持自定义 Header 的调用方应优先使用 `X-BubblePilot-Webhook-Secret`。
