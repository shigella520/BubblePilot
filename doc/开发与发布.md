# BubblePilot 开发与发布

## 技术基线

| 项目 | 要求 |
| --- | --- |
| Node.js | 22 或更高 |
| TypeScript | 5、ESM、严格类型检查 |
| 包管理器 | pnpm 11，由 `packageManager` 固定 |
| 数据库 | PostgreSQL 16 |
| Web | Fastify 5、Vue 3、Vite |
| 测试 | Vitest、Fastify `inject`、PostgreSQL 集成测试 |

应用组装放在 `app/`，领域逻辑放在 `modules/`，机器合同放在 `contracts/`。供应商 Payload 只能进入相应适配器和契约，不允许业务控制器直接依赖 BlueBubbles 原始 JSON。

## 本地开发

需要 Git、Node.js 22 + Corepack、Docker Compose，以及 BlueBubbles 测试实例或仓库内虚构 Fixture。

```bash
corepack enable
pnpm install
cp .env.example .env.local
```

把 `.env.local` 中 `DATABASE_URL` 的主机从 Compose 服务名 `postgres` 改为 `127.0.0.1`，替换所有 `CHANGE_ME`。本地密码也只保存哈希：

```bash
printf '输入密码（输入不会显示）：' >&2
IFS= read -r -s BUBBLEPILOT_PLAIN_PASSWORD
printf '\n' >&2
printf '%s' "$BUBBLEPILOT_PLAIN_PASSWORD" | pnpm auth:hash
unset BUBBLEPILOT_PLAIN_PASSWORD
```

分别生成登录与敏感操作哈希，并在 `.env.local` 中用单引号包裹。不要把明文密码作为命令参数。

启动后端：

```bash
pnpm db:migrate:local
pnpm dev:local
```

需要独立 Web 热更新时另开终端：

```bash
pnpm dev:web
```

应用健康检查为 `/health/live` 和 `/health/ready`。开发 Fixture 只能使用虚构聊天、虚构标识和占位 Secret。

## 开发原则

- 从产品需求和验收条件开始，以一个可独立验证的垂直切片完成变更。
- 外部依赖通过适配器隔离；节点通过注册表扩展。
- 节点配置是数据，激活前必须校验，不能引入任意脚本执行。
- 数据库迁移只追加，不修改已合并或发布的迁移。
- Schema、环境变量、认证、权限、消息语义或保留策略变化必须同步文档和测试。
- 日志和诊断默认脱敏，不因排障临时写入正文、Prompt、Token 或原始响应。

## 验证命令

提交前至少运行：

```bash
pnpm verify
pnpm security:check
docker compose config
```

`pnpm verify` 依次检查：

1. Prettier；
2. ESLint；
3. TypeScript 类型；
4. Vitest 单元和 API 测试；
5. 运维 Shell 语法与合同；
6. OpenAPI 路由、引用、路径参数和环境变量合同；
7. Markdown 本地链接；
8. 服务端与 Web 生产构建。

`pnpm security:check` 单独查询依赖公告，并在生产依赖包含中危或更高漏洞时失败。该检查由 CI 和开发镜像发布工作流执行。升级依赖后仍需运行完整测试和镜像构建，不能只依赖公告扫描。

本机安装 ShellCheck 时额外运行：

```bash
shellcheck scripts/*.sh
```

设置 `TEST_DATABASE_URL` 后，Vitest 会运行 PostgreSQL 仓储集成测试。CI 会在 PostgreSQL 16 上先执行全部迁移，再验证消息事务、唯一约束、工作流恢复、AI 诊断、管理会话、内容保留和受控导出。

高风险变更的回归边界：

| 变更 | 至少验证 |
| --- | --- |
| Webhook / 适配器 | Secret、Payload、重复事件、监听过滤、供应商字段 Fixture |
| 工作流 / 节点 | Schema、图校验、叶子 I/O 超时、Retry、分支、版本锁定和幂等 |
| AI / 搜索 | Provider 协议、Fallback、降级、工具上限、零结果、脱敏 |
| 认证 / Web | 会话、二次验证、过期收起、服务端越权拒绝和审计 |
| 导出 / 保留 | 冻结快照、所有者隔离、上限、过期、内容清理互斥 |
| 运维 / 迁移 | Compose、健康检查、备份恢复、升级和回滚路径 |

Web 异步交互和可靠性演练的有限集合见[验收与演练](验收与演练.md)。

## 数据库迁移

迁移文件位于 `migrations/`，按名称升序执行；`schema_migrations` 保存已应用版本，迁移器使用 PostgreSQL advisory lock 防止并发迁移。

规则：

- 每个生产数据模型变化新增一个 SQL 文件；
- 不修改已合并或已发布的迁移；
- 迁移、代码、OpenAPI/Schema、回归测试和升级说明在同一个 PR；
- 应用镜像启动时先迁移，失败则不启动服务；
- 破坏性或不可逆变化必须在 Release Notes 给出备份、兼容和回滚决定。

## 日志与排障开发

每个请求使用 UUID `correlationId`。普通日志只包含事件键、实体 ID、状态和错误码。

排查 AI 时按 `executionId → nodeId → agentTurn → round/sequence` 查看 Attempt，再用供应商请求 ID、HTTP 状态、响应大小、哈希和 Token 计数判断问题。不要把完整 Prompt 或聊天正文复制到日志。

排查搜索时查看 `aiToolExecutions` 的查询、语言、引擎、规范化结果、零结果和不可用引擎。HTTP 200 零结果是 `succeeded + no_results`，不等于后端宕机；旧 `required` 已兼容为自动搜索，零结果不再强制节点失败。

## 分支、Commit 与 Pull Request

采用短期功能分支，不维护长期 `dev` 分支：

```text
main (protected)
  └── codex/<short-kebab-description> → Pull Request → main
```

- 分支从最新 `main` 创建，一个分支只处理一个明确目标，合并后删除。
- `main` 只接受 Pull Request；紧急修复也不绕过 Review 和 CI。
- 默认 Squash Merge，PR 标题成为 `main` 的最终 Commit。

Commit 和 PR 标题使用英文 Conventional Commit：

```text
<type>(<scope>): <imperative summary>
```

允许 `feat`、`fix`、`docs`、`test`、`refactor`、`chore`、`ci`、`build`、`perf`、`release`。示例：

```text
feat(workflow): add conditional node
fix(reply): prevent duplicate outgoing messages
docs(deploy): clarify webhook setup
```

PR 必须说明：

- 关联需求或问题；
- 改动范围与明确不包含的内容；
- 数据库、配置、权限和兼容性影响；
- 验证命令与结果；
- 升级、备份、人工操作和失败回滚方式。

Webhook、发送、凭据、消息搜索、导出和删除变化至少需要一次额外 Review。CI 未通过、存在未解决高优先级意见或缺少迁移说明时不得合并。

## 版本与镜像

正式版本使用 SemVer：

- `MAJOR`：不兼容 API、工作流 Schema、数据语义或升级方式；
- `MINOR`：向后兼容的新功能或节点；
- `PATCH`：向后兼容修复和安全修复。

Git Tag 和 GitHub Release 使用 `vX.Y.Z`；镜像位于 `ghcr.io/shigella520/bubblepilot`：

| 标签 | 用途 |
| --- | --- |
| `X.Y.Z` | 不可移动的正式精确版本 |
| `latest` | 最新正式版本，可移动 |
| `sha-<commit>` | 精确提交验证和回滚 |
| `dev` | 手动开发构建，不用于长期生产 |

CI 行为：

- 目标 `main` 的 PR、`main` 推送和手动 CI：完整验证并试构建镜像，不推送。
- `Publish Dev Image`：在 PostgreSQL 16 + pgvector 环境执行完整验证、扩展准备和备份恢复演练后推送 `dev` 和 `sha-<commit>`。
- 指向 `main` 历史的 `vX.Y.Z` Tag：完整验证后推送 `X.Y.Z`、`latest` 和 `sha-<commit>`。

## 正式发布

1. 从最新 `main` 创建 `codex/release-vX.Y.Z`。
2. 更新应用版本、Schema 版本、README 和升级说明。
3. 检查迁移、环境变量、权限、备份和回滚。
4. 运行完整验证与目标环境演练。
5. 通过 PR 合并到 `main`。
6. 在该提交创建不可变 Tag `vX.Y.Z`。
7. 等待 CI 发布精确镜像，再创建同名 GitHub Release。
8. 获得实例部署授权后，按[运维操作手册](运维操作手册.md)部署该版本的精确镜像并验收。

Release Notes 至少包含功能与修复、已知限制、API/工作流/BlueBubbles 兼容性、数据库迁移、环境变量、安全影响、备份、升级、验证和回滚。发布失败不重写 Tag 或精确镜像；修复后发布新的 PATCH。

## 文档规则

- 产品、设计、开发、部署和发布文档以简体中文为权威来源。
- `README.md` 为默认用户入口；`README.en.md` 和 `README.zh-TW.md` 保持核心能力、部署顺序和安全含义一致。
- 代码名、字段、环境变量、错误码和 Commit 使用英文。
- 中文专题文档放在 `doc/`，机器合同放在 `contracts/`，图表使用仓库内 SVG/PNG 或 Mermaid。
- 新功能优先更新现有权威文档；不要为一次迭代创建长期“进度快照”或重复说明。
- 创建 PR 前运行 `pnpm docs:check`，确保本地链接和仓库结构有效。

## 长期检索开发验证

PostgreSQL 测试先运行普通迁移和 `pnpm db:prepare-memory`，再设置 `TEST_DATABASE_URL` 运行测试。CI 使用固定 pgvector PostgreSQL 16 镜像，并执行 `scripts/test-memory-upgrade.sh` 验证逻辑备份恢复。普通不带扩展的外部实例必须保持功能关闭时可运行。

`pnpm memory:evaluate` 使用仓库内四十个虚构问题和十个保留验证题，通过 `MEMORY_EVAL_URL`、可选 `MEMORY_EVAL_PROTOCOL|MODEL|DIMENSIONS|QUERY_PREFIX|SECRET` 配置开发评测端点。这些是开发脚本变量，不是应用运行时合同。脚本评估关键词、向量和 RRF 候选 Recall@5；不能代替答案支持性、近期原文基线与 Agent 自主调用的真实模型验收。

`pnpm memory:benchmark` 只允许 `MEMORY_BENCH_DATABASE_URL` 指向名称以 `_memory_bench` 结尾的独立数据库，使用临时表生成 1 万及 10 万条 1024 维虚构向量。输出仅为精确 SQL 查询基准，不代表完整 RAG 延迟或实际索引吞吐。

### 补建进度验证

补建进度变更追加迁移 0047，不通过重建数据库部署。运行 `pnpm verify` 时，设置 `TEST_DATABASE_URL` 可验证固定成员计数、清理和旧任务恢复；纯 ETA 与前端轮询使用可控时钟测试。统计性能评估使用独立的虚构 PostgreSQL 数据库，不访问生产归档，详细测量边界见验收与演练中的补建进度记录。

### Agent 配额评测

`pnpm agent:evaluate` 是独立的开发评测入口，必须显式提供 `AGENT_EVAL_URL`、`AGENT_EVAL_MODEL`，可选 `AGENT_EVAL_SECRET` 与 `AGENT_EVAL_PROTOCOL=chat-completions|responses`。这些变量只用于评测脚本，不属于应用运行配置。未提供端点/模型时退出码为 2，明确表示未运行，不会自动读取生产数据库或复用生产凭据。

评测固定使用虚构成员、日期和工具数据，运行问候、最近发言、历史与联网组合、七天逐日查询、二十天预算耗尽五个场景。脚本比较当前 AgentRunner 与 `AGENT_EVAL_BASELINE_REF` 指定的旧提交（默认 `b01790fb70c8065e02fa76a861f17a5025cc1669`），需要带 Git 历史的开发检出；临时基线模块在正常退出时删除，不能作为服务端生产入口。基线历史工具模拟旧的 2 次搜索/3 次展开及 6,000 字符限制；工具数据和延迟是 Fixture，不代表数据库性能。

输出 JSONL 包含场景、基线提交、模型、工具序列、调用次数、模型轮数、耗时、Token（供应商未返回时为 null）、回答与人工验收标准。结果均标为 `requires-human-review`；检查完整性、工具选择、时间事实及预算解释，不用关键词匹配冒充答案质量审核。确定性单元/集成测试结果与真实模型评测分别记录。

### 五工具验证入口

使用 TEST_DATABASE_URL 指向独立虚构数据库执行 pnpm verify，先执行 db:migrate 与 db:prepare-memory。另运行 pnpm security:check 和 docker compose --env-file .env.example config --quiet。

CHAT_QUERY_BENCH_DATABASE_URL 指向名称以 _test 结尾的独立数据库后，运行 pnpm chat:benchmark。在单连接 TEMP 表生成 1 万/10 万虚构消息，执行实际仓储查询并输出 p50/p95 和原文查询 EXPLAIN ANALYZE；临时表在断开连接时消失，不使用归档正文。

pnpm agent:evaluate 新增每天最早发言、字面计数与原文组合、身份歧义场景；历史预算 runner 与当前 runner 使用同一当前工具集合，以比较预算而不是混淆工具有无。此入口使用有限虚构工具响应，不替代确定性 SQL 测试；输出 calls/turns/durationMs/模型 token 用量与人工评估项。未配置开发端点时明确退出为待运行，不把模拟测试记为模型通过。NAS 联调仍需另行记录真实工具执行及回答质量。


### 聊天摘要退休验证（迁移 0052）

配置独立虚构 `TEST_DATABASE_URL` 后运行 `pnpm verify`。新增迁移集成测试会创建并删除一个临时 `_test` 数据库，测试账号需有 CREATEDB 权限；测试按历史迁移构建旧 Schema、插入虚构摘要及保留数据后运行 0052。普通数据库与生产聊天不会作为迁移测试目标。

`pnpm agent:evaluate` 增加 raw-window-missing-history 与 raw-window-enough-evidence 场景：分别检查窗口缺口时调用原文工具、可见证据足够时直接回答。真实模型结果与确定性测试分开记录；未提供开发端点时保持待运行，不自动复用生产凭据。窗口前缀稳定的确定性测试不能替代 Provider 缓存命中与答案质量评测。


### 可选搜索引擎验证

修改 `deploy/searxng/` 时，除标准验证外，运行 `python3 -m unittest discover -s deploy/searxng -p 'test_*.py' -v` 和 `docker compose -f deploy/searxng/compose.yaml config --quiet`。Python 测试只使用标准库，不依赖生产密钥。该扩展通过文件挂载交付，不包含在 BubblePilot 应用镜像中；发布应用镜像不会自动升级 NAS 上的扩展文件。

## 轻量沙箱运行镜像验证

[运行镜像验证说明](../plugins/opensandbox/runtime/README.md) 提供离线虚构数据冒烟测试和本地 Docker 基线测量。CI 增加 amd64 镜像构建、512 MiB 工作负载与系统/Python HIGH/CRITICAL 漏洞阻断。Dev 发布增加第三个运行镜像，实际待推送镜像经测试扫描后原样推送，不自动部署。
