# BubblePilot 部署与运维

## 1. 部署目标

M1 使用 Docker Compose 部署 TypeScript 模块化单体与 PostgreSQL 16：

```text
reverse proxy / HTTPS
        ↓
BubblePilot application
        ↓
PostgreSQL
```

应用容器启动时先运行只追加迁移，再启动 HTTP 服务。消息队列和独立 Worker 不是首期必需组件。

## 2. 首次启动

```bash
cp .env.example .env
```

至少完成以下配置：

1. 把 `POSTGRES_PASSWORD` 和 `DATABASE_URL` 中的数据库密码改成同一个强密码。
2. 为 `API_ACCESS_TOKEN` 和 `BLUEBUBBLES_WEBHOOK_SECRET` 分别生成至少 32 字符的随机值，不能复用。
3. 把需要归档的 BlueBubbles Chat GUID 以逗号分隔写入 `MONITORED_CHAT_IDS`；留空时不会归档任何消息正文。
4. 保留后续里程碑变量的占位值即可，M1 不读取 BlueBubbles REST、登录密码、二次验证和 AI 配置。

检查并启动：

```bash
docker compose config
docker compose up -d --build
docker compose ps
```

Compose 默认只把应用映射到宿主机 `127.0.0.1:8080`，应通过受控反向代理提供 HTTPS，不直接把 PostgreSQL 暴露到宿主机端口。

### 2.1 从当前源码构建

`docker compose up -d --build` 使用当前工作区的 Dockerfile 构建应用，并以 `BUBBLEPILOT_IMAGE` 指定的名称保存在本机。该方式适合本地开发和尚未发布镜像的分支。

### 2.2 使用 Dev 或 SHA 镜像验证部署

手动运行 GitHub Actions 的 `Publish Dev Image` 后，工作流会同时发布：

```text
ghcr.io/shigella520/bubblepilot:dev
ghcr.io/shigella520/bubblepilot:sha-<commit>
```

把 `.env` 中的 `BUBBLEPILOT_IMAGE` 设置为需要验证的标签，然后拉取并启动，不在服务器重新构建：

```bash
docker compose pull app
docker compose up -d --no-build
docker compose ps
```

`dev` 会随下一次手动发布移动。验证结果需要复现、比较或回滚时，应固定同一次工作流产生的 `sha-<commit>`。

首次发布后应在 GitHub Packages 检查 `bubblepilot` 容器包的可见性。公开镜像可以直接拉取；私有镜像需要先使用具备 `read:packages` 权限的凭据执行 `docker login ghcr.io`，凭据不能写入 `.env`、Compose 或部署日志。

正式环境使用 `ghcr.io/shigella520/bubblepilot:X.Y.Z`，不使用 `dev`；是否使用可移动的 `latest` 由运维者明确决定。

## 3. BlueBubbles 配置

在 BlueBubbles Server 新建 Webhook，订阅 `New Messages`，URL 使用：

```text
https://bubblepilot.example.com/api/v1/webhooks/bluebubbles?token=<BLUEBUBBLES_WEBHOOK_SECRET>
```

BlueBubbles 当前不会为 Webhook 附加签名头，所以共享密钥随 URL 查询参数发送。反向代理必须关闭该路径的查询串访问日志；BubblePilot 自身已关闭默认请求日志，不记录该 URL。

在一个已加入 `MONITORED_CHAT_IDS` 的虚构测试聊天发送消息，Webhook 应返回 `202` 和 `archived`。相同事件再次发送应返回 `duplicate`；范围外聊天应返回 `ignored`。

## 4. 健康和查询

```bash
curl --fail http://127.0.0.1:8080/health/live
curl --fail http://127.0.0.1:8080/health/ready
curl --fail -H "Authorization: Bearer $API_ACCESS_TOKEN" \
  http://127.0.0.1:8080/api/v1/chats
```

| 接口 | 200 含义 | 失败含义 |
| --- | --- | --- |
| `/health/live` | Node.js 进程可响应 | 进程或网络不可用 |
| `/health/ready` | PostgreSQL 可查询且 M1 迁移已应用 | 返回 `503`，数据库或迁移不可用 |

查询 API 使用 M1 的只读 Bearer Token。M4 会增加 Web 登录、会话和敏感操作二次验证。

## 5. 日志和诊断

```bash
docker compose logs --tail=200 app
docker compose logs --tail=200 postgres
```

应用日志只记录 `correlationId`、事件键、状态和内部实体 ID，不记录消息正文、原始 Payload 或 Secret。故障排查顺序：

1. 按 `correlationId` 确认请求是否到达。
2. 区分 `archived`、`ignored`、`duplicate` 和 `failed`。
3. 检查 `MONITORED_CHAT_IDS` 是否使用 BlueBubbles Chat GUID，而不是显示名称。
4. 检查 PostgreSQL 就绪状态和迁移输出。
5. 不通过手工插库或删除幂等记录来重复处理生产消息。

## 6. 备份和恢复

- M1 至少备份 PostgreSQL 中的 `schema_migrations`、`inbound_events`、`chats` 和 `messages`。
- Secret 不与数据库备份放在同一个无保护位置。
- 恢复后检查迁移版本、聊天监听状态和 Webhook 幂等记录。
- 定期进行恢复演练，记录恢复时间和失败项。

## 7. 升级和回滚

升级前：

- 阅读 Release Notes；
- 备份数据库；
- 运行 `docker compose config`；
- 检查新增迁移与环境变量；
- 准备上一版本镜像和回滚步骤。

修改 `.env` 中的 `BUBBLEPILOT_IMAGE` 为目标精确版本后执行：

```bash
docker compose pull app
docker compose up -d --no-build
```

数据库迁移只前向执行。回滚应用镜像不会自动回滚数据库；若迁移不可逆，发布说明必须明确恢复策略。
