# BubblePilot 部署与运维

## 1. 部署目标

BubblePilot 使用 Docker Compose 部署 TypeScript 模块化单体、PostgreSQL 16 和 SearXNG：

```text
reverse proxy / HTTPS
        ↓
BubblePilot application
        ├── PostgreSQL
        └── SearXNG ──→ external search engines
```

SearXNG 只作为 AgentRunner 的可选联网搜索后端，不是应用数据库，也不保存工作流事实；Compose 默认不把它的端口映射到宿主机。`ENABLE_WEB_SEARCH=false` 时应用不会发起搜索调用。应用容器启动时先运行只追加迁移，再使用 `exec` 启动 HTTP 服务，使 Node.js 成为容器 PID 1 并直接接收停止信号。迁移失败时容器不会启动应用；正常停止时应用会关闭保留任务和数据库连接。Compose 为应用保留 330 秒停止宽限，覆盖单次工作流最长 300 秒的预算，升级脚本不应使用更短的强制停止覆盖它。消息队列和独立 Worker 不是首期必需组件。

## 2. 首次启动

```bash
cp .env.example .env
```

至少完成以下配置：

1. 把 `POSTGRES_PASSWORD` 和 `DATABASE_URL` 中的数据库密码改成同一个强密码。
2. 为 `API_ACCESS_TOKEN` 和 `BLUEBUBBLES_WEBHOOK_SECRET` 分别生成至少 32 字符的随机值，不能复用。
3. 可把首次启动即需归档的 BlueBubbles Chat GUID 以逗号分隔写入 `MONITORED_CHAT_IDS`；它只决定尚未发现聊天的初始状态，聊天出现后由数据库监听配置管理。留空时新聊天默认不归档正文。
4. 设置 `BLUEBUBBLES_SERVER_URL` 和 `BLUEBUBBLES_ACCESS_TOKEN`；按服务能力选择 `BLUEBUBBLES_SEND_METHOD`，默认使用 `private-api`。
5. AI Provider 只能在 Web 管理端直接填写 API Key；服务端会使用 `SETTINGS_ENCRYPTION_KEY` 加密保存，列表、详情和日志不会回显原值。
6. 为 SearXNG 生成独立的至少 32 字符随机 `SEARXNG_SECRET`。联网搜索默认关闭；需要启用时设置 `ENABLE_WEB_SEARCH=true`。可选的 `SEARXNG_ENGINES` 用逗号分隔搜索引擎，留空时使用 SearXNG 配置；`SEARXNG_LANGUAGE` 默认 `zh-CN`：

```dotenv
ENABLE_WEB_SEARCH=true
SEARXNG_SECRET=CHANGE_ME_WITH_AT_LEAST_32_RANDOM_CHARACTERS
SEARXNG_ENGINES=
SEARXNG_LANGUAGE=zh-CN
WEB_SEARCH_TIMEOUT_MS=8000
WEB_SEARCH_MAX_RESULTS=5
```

7. 为登录密码和敏感操作密码分别生成 scrypt 哈希，两个密码不能复用。哈希包含 `$`，写入 `.env` 时必须使用单引号：

```bash
read -rs "BUBBLEPILOT_PLAIN_PASSWORD?Password: "
printf '%s' "$BUBBLEPILOT_PLAIN_PASSWORD" | pnpm auth:hash
unset BUBBLEPILOT_PLAIN_PASSWORD
```

把两次输出分别写入 `APP_LOGIN_PASSWORD_HASH` 与 `SENSITIVE_OPERATION_PASSWORD_HASH`。默认管理会话有效 12 小时，二次验证有效 5 分钟，可通过对应 TTL 环境变量调整。

8. 确认消息内容保留期。默认从消息归档入库起保留正文与附件元数据 90 天；到期只清理敏感内容，保留幂等和执行追踪所需元数据。设为 `0` 会关闭自动清理，只应在明确接受无限期保留风险时使用：

```dotenv
MESSAGE_RETENTION_DAYS=90
```

9. 按实例负载确认可靠性上限。默认管理 API 每分钟 600 次、Webhook 每分钟 300 次；工作流最多并发 4 条、等待 64 条、最长等待 30 秒。以下变量均为硬边界，不应靠无限增大来掩盖慢 Provider 或数据库故障：

```dotenv
RATE_LIMIT_WINDOW_SECONDS=60
ADMIN_RATE_LIMIT_MAX=600
WEBHOOK_RATE_LIMIT_MAX=300
WORKFLOW_MAX_CONCURRENCY=4
WORKFLOW_QUEUE_CAPACITY=64
WORKFLOW_QUEUE_WAIT_MS=30000
STALE_RETRY_SECONDS=300
```

检查并启动：

```bash
docker compose config
docker compose up -d --build
docker compose ps
```

Compose 默认只把应用映射到宿主机 `127.0.0.1:8080`，应通过受控反向代理提供 HTTPS，不直接把 PostgreSQL 或 SearXNG 暴露到宿主机端口。

### 2.1 从当前源码构建

`docker compose up -d --build` 使用当前工作区的 Dockerfile 构建应用，并以 `BUBBLEPILOT_IMAGE` 指定的名称保存在本机。该方式适合本地开发和尚未发布镜像的分支。

### 2.2 使用 Dev 或 SHA 镜像验证部署

手动运行 GitHub Actions 的 `Publish Dev Image` 后，工作流会同时发布：

```text
ghcr.io/shigella520/bubblepilot:dev
ghcr.io/shigella520/bubblepilot:sha-<commit>
```

把 `.env` 中的 `BUBBLEPILOT_IMAGE` 设置为需要验证的标签，然后拉取并启动，不在服务器重新构建：

```bash
docker compose pull app
docker compose up -d --no-build
docker compose ps
```

`dev` 会随下一次手动发布移动。验证结果需要复现、比较或回滚时，应固定同一次工作流产生的 `sha-<commit>`。

首次发布后应在 GitHub Packages 检查 `bubblepilot` 容器包的可见性。公开镜像可以直接拉取；私有镜像需要先使用具备 `read:packages` 权限的凭据执行 `docker login ghcr.io`，凭据不能写入 `.env`、Compose 或部署日志。

正式环境使用 `ghcr.io/shigella520/bubblepilot:X.Y.Z`，不使用 `dev`；是否使用可移动的 `latest` 由运维者明确决定。

## 3. BlueBubbles 配置

BlueBubbles 的连接参数支持两种来源。首次启动时必须通过环境变量提供合法的
`BLUEBUBBLES_SERVER_URL`、`BLUEBUBBLES_ACCESS_TOKEN` 和
`BLUEBUBBLES_WEBHOOK_SECRET`，应用会以它们作为回退配置。管理员登录 Web 管理端后，
可在“设置”页面保存 Server URL、Access Token、Webhook Secret、发送方式和请求超时；
凭据会使用 `SETTINGS_ENCRYPTION_KEY` 加密写入 PostgreSQL，后续修改无需重建容器并会在
下一次请求前生效。页面不会回显任何 Secret，留空 Secret 表示保留已有值。保存设置需要
敏感操作二次验证，并使用版本号避免覆盖他人刚保存的修改。

设置页的“验证服务连接”会使用当前配置请求 BlueBubbles `/api/v1/server/info`，用于区分
Server URL、网络或 Access Token 问题。该检查是只读请求，不代表 Webhook 已经投递成功；
如果 REST 验证成功但聊天监听仍为空，应继续检查 BlueBubbles Webhook URL、查询参数中的
Webhook Secret、反向代理可达性，以及 BlueBubbles Server 的 Webhook 投递日志。

`SETTINGS_ENCRYPTION_KEY` 应在正式环境中设置为独立的高熵随机值，并在迁移、重启和回滚
期间保持不变；未设置时暂时回退到 `API_ACCESS_TOKEN`，仅用于兼容旧部署。密钥丢失会导致
数据库中的运行时凭据无法解密，需要重新在设置页录入。

### 管理会话 Cookie 的 HTTPS 策略

`SESSION_COOKIE_SECURE` 是可选特性，不绑定 `NODE_ENV`：

- `auto`（默认）：请求经 HTTPS 或反向代理通过 `X-Forwarded-Proto: https` 表示 HTTPS 时添加 `Secure`；HTTP 访问不添加，适合同时支持本地 HTTP 验证和 HTTPS 生产反代。
- `true`：始终添加 `Secure`，仅适用于确保浏览器通过 HTTPS 访问的部署。
- `false`：始终不添加 `Secure`，只建议用于受控的纯 HTTP 内网验证。

修改后需要重启应用容器；无论策略如何，Cookie 仍保持 `HttpOnly`、`SameSite=Strict`。

在 BlueBubbles Server 新建 Webhook，订阅 `New Messages`，URL 使用：

```text
https://bubblepilot.example.com/api/v1/webhooks/bluebubbles?token=<BLUEBUBBLES_WEBHOOK_SECRET>
```

BlueBubbles 当前不会为 Webhook 附加签名头，所以共享密钥随 URL 查询参数发送。反向代理必须关闭该路径的查询串访问日志；BubblePilot 自身已关闭默认请求日志，不记录该 URL。

在一个已加入 `MONITORED_CHAT_IDS` 的虚构测试聊天发送消息，Webhook 应返回 `202` 和 `archived`。相同事件再次发送应返回 `duplicate`；范围外聊天应返回 `ignored`。

## 4. AI Provider 与路由配置

推荐在 Web 管理端创建 Provider 并直接填写 API Key；也可以通过受 Bearer Token 保护的 API 创建。`secret` 是只写字段，服务端会加密保存，不会在响应中返回：

```bash
curl --fail-with-body -X POST \
  -H "Authorization: Bearer $API_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  http://127.0.0.1:8080/api/v1/ai/providers \
  --data '{
    "name": "Primary AI",
    "apiKind": "responses",
    "baseUrl": "https://api.openai.com/v1",
    "model": "CHANGE_ME",
    "secret": "sk-example"
  }'
```

使用返回的 Provider UUID 创建路由；工作流 `ai-chat@1` 节点通过返回的路由 UUID 引用它：

```bash
curl --fail-with-body -X POST \
  -H "Authorization: Bearer $API_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  http://127.0.0.1:8080/api/v1/ai/routes \
  --data '{
    "name": "Default AI route",
    "providerIds": ["CHANGE_ME_PROVIDER_UUID"],
    "fallbackEnabled": true,
    "retryPolicy": {"maxRounds": 2, "initialDelayMs": 500},
    "degradePolicy": {"failureThreshold": 3, "cooldownMs": 60000},
    "enabled": true
  }'
```

能力测试路径为 `POST /api/v1/ai/providers/{providerId}/test`。它只调用指定 Provider，使用固定虚构输入，不读取聊天归档、不执行 Fallback，也不修改生产健康计数；结果分别展示基础连接、Function Calling 和 Provider 托管搜索，某项可选能力失败不会把基础连接改成失败。完整字段和乐观版本规则见[接口与配置契约](接口与配置契约.md)。

### 4.1 配置 Agent 联网搜索

AI 节点的 `webSearch` 支持以下策略：

| 策略       | 运行行为                           | 适用场景                   |
| ---------- | ---------------------------------- | -------------------------- |
| `disabled` | 不向模型提供搜索能力               | 摘要、改写和固定知识问答   |
| `auto`     | 由模型判断是否调用搜索             | 普通聊天 Bot，推荐默认使用 |
| `required` | 至少取得一条可用结果，否则稳定失败 | 必须依据实时信息的流程     |

`webSearchSources=full|compact|hidden` 只控制聊天回复是否展示完整来源、末尾最多两个精简来源或隐藏来源；三种模式都保留管理端工具轨迹。

路由发布前应先在 AI Provider 页面刷新能力探测。已验证托管搜索的 Provider 会优先使用原生能力；否则 Provider 必须通过 Function Calling 探测，并由 BubblePilot 的进程内 AgentRunner 调用 SearXNG。一次 AI 节点最多执行 4 个模型轮次和 3 次工具调用，单次搜索默认 8 秒、最多返回 5 条规范化结果。网页文本属于不可信外部材料，不应通过提示词把它提升为系统指令。

AI Provider 页面会显示“搜索后端：searxng · 可用/不可用”。该状态通过 `/healthz` 判断，不用固定关键词试搜，因此单个搜索引擎的 CAPTCHA 或临时失败不会误报为整个后端不可用。实际查询中的零结果、放宽查询、返回条目和 `unresponsive_engines` 会记录在执行详情的工具轨迹中。

## 5. 健康和查询

```bash
curl --fail http://127.0.0.1:8080/health/live
curl --fail http://127.0.0.1:8080/health/ready
curl --fail -H "Authorization: Bearer $API_ACCESS_TOKEN" \
  http://127.0.0.1:8080/api/v1/chats
```

| 接口            | 200 含义                          | 失败含义                       |
| --------------- | --------------------------------- | ------------------------------ |
| `/health/live`  | Node.js 进程可响应                | 进程或网络不可用               |
| `/health/ready` | PostgreSQL 可查询且当前迁移已应用 | 返回 `503`，数据库或迁移不可用 |

查询与配置 API 兼容高熵 Bearer Token，也支持 Web 管理会话。Web 登录只建立普通管理会话；消息正文、工作流发布或启停、Provider/Route 变更、健康重置等操作还必须完成短时效二次验证。服务端只保存会话 Token 的 SHA-256，不保存 Cookie 原文；登录失败、二次验证和敏感操作结果均进入审计记录。

### 5.1 数据导出处理

管理端的数据导出只针对单个当前已监听聊天，要求明确时间范围和数据类型。系统先创建 5 分钟有效的冻结预览，完成二次验证并显式确认后提供 10 分钟有效的 JSON Lines 下载。应用不在容器或共享卷中写入临时正文文件，因此无需配置导出目录或文件清理任务。

导出文件应只下载到受控设备，并按数据库备份同等敏感等级保存、传输和销毁。下载响应设置 `Cache-Control: no-store`；反向代理不得缓存 `/api/v1/exports/*/download`，也不得记录响应正文。若下载返回过期、撤销、聊天不可用或快照冲突，应重新创建预览，不要绕过服务端检查或直接查询数据库拼接文件。

## 6. 日志和诊断

```bash
docker compose logs --tail=200 app
docker compose logs --tail=200 postgres
docker compose logs --tail=200 searxng
scripts/diagnose.sh
```

应用日志只记录 `correlationId`、事件键、状态和内部实体 ID，不记录消息正文、原始 Payload 或 Secret。故障排查顺序：

1. 按 `correlationId` 确认请求是否到达。
2. 区分入站 `archived`、`ignored`、`duplicate`，以及执行 `running`、`retrying`、`succeeded`、`failed`、`dead-lettered`。
3. 检查 `MONITORED_CHAT_IDS` 是否使用 BlueBubbles Chat GUID，而不是显示名称。
4. 检查 PostgreSQL 就绪状态和迁移输出。
5. 联网搜索失败时先查看 AI Provider 页面的 SearXNG 健康状态，再在执行详情区分 Provider Attempt、工具协议错误、零结果和部分引擎故障；SearXNG 故障不应表现为 Provider 自动降级。
6. 回复状态为 `unknown` 时先确认供应商最终状态，不通过手工插库、删除幂等记录或直接重放来重复发送。

设置只存在于当前 Shell 的 `BUBBLEPILOT_API_ACCESS_TOKEN` 后，`scripts/diagnose.sh` 还会查询 `/api/v1/operations/status`，输出死信、卡住的 Retry、未知出站、Provider 降级、执行容量和消息保留任务摘要。脚本不会读取或打印 `.env` 中的 Token。

消息保留任务在应用就绪后立即运行，之后每小时处理最多 10,000 条。它会延期处理仍在自动化判定、运行/人工恢复或有效导出快照中的消息；实际清理批次以 `message.content.retention` 写入系统审计。`MESSAGE_RETENTION_FAILED` 表示最近一次任务失败，`MESSAGE_RETENTION_BACKLOG` 表示单批达到上限、仍可能存在积压；前者应先检查数据库与迁移，后者可等待后续小时批次并观察数量是否下降。

Web 管理端“恢复队列”使用 `retrying,failed,dead-lettered,closed` 状态筛选。人工重试和人工关闭都要求二次验证并写入审计。`retrying` 只有在 `nextRetryAt` 已超过 `STALE_RETRY_SECONDS` 后才能人工恢复；阈值内返回 `EXECUTION_RETRY_STILL_ACTIVE`，可以等待自动重试或人工关闭。人工关闭和逾期恢复都会阻止仍在等待的旧执行器继续运行。若详情包含 `sending`、`unknown` 或 `confirmed` 出站记录，重试会被服务端拒绝；先核对 BlueBubbles 最终结果，再选择关闭处理。

## 7. 备份和恢复

- 至少备份 PostgreSQL 中的 `schema_migrations`、入站与消息表、工作流与触发器表、Provider/路由配置、健康事件、执行轨迹、出站发送、管理会话元数据、审计事件和导出任务记录。
- Secret 不与数据库备份放在同一个无保护位置。
- 恢复后检查迁移版本、聊天监听状态、发布工作流、启用触发器、Webhook 与回复幂等记录。
- 定期进行恢复演练，记录恢复时间和失败项。

创建权限为当前用户私有的 PostgreSQL custom-format 备份及 SHA-256 文件：

```bash
scripts/backup-postgres.sh
```

在同一 PostgreSQL 容器内创建随机命名的临时数据库、完整恢复、查询迁移与关键表，最后自动删除该临时数据库：

```bash
scripts/verify-postgres-backup.sh backups/bubblepilot-YYYYMMDDTHHMMSSZ.dump
```

校验脚本会先读取同名 `.sha256` 文件并核对备份内容，再创建临时数据库；校验和缺失或不匹配时不会进入恢复步骤。脚本只删除自身生成且通过固定前缀检查的临时数据库，不接受自定义恢复库名，也不会覆盖生产数据库。备份文件和校验和仍需复制到受控的异机位置。

## 8. 升级和回滚

升级前：

- 阅读 Release Notes；
- 备份数据库；
- 运行 `docker compose config`；
- 检查新增迁移与环境变量；
- 准备上一版本镜像和回滚步骤。

可把刚生成的备份传给升级前检查，一次完成 Compose、恢复、健康和运行状态检查：

```bash
scripts/preflight-upgrade.sh backups/bubblepilot-YYYYMMDDTHHMMSSZ.dump
```

修改 `.env` 中的 `BUBBLEPILOT_IMAGE` 为目标精确版本后执行：

```bash
docker compose pull app
docker compose up -d --no-build
```

数据库迁移只前向执行。回滚应用镜像不会自动回滚数据库；若迁移不可逆，发布说明必须明确恢复策略。

可复现演练步骤和执行记录见[可靠性演练记录](可靠性演练记录.md)。
