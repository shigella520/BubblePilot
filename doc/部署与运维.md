# BubblePilot 部署与运维

## 部署结构

```text
BlueBubbles Server ──Webhook──→ reverse proxy / HTTPS
                                      ↓
                              BubblePilot application
                                ├── PostgreSQL 16
                                └── SearXNG ──→ search engines
```

Compose 只把 BubblePilot 映射到宿主机 `127.0.0.1:8080`；PostgreSQL 和 SearXNG 不开放宿主机端口。SearXNG 只在 AI 节点联网时使用，不保存 BubblePilot 业务事实。

应用容器启动时先执行只追加数据库迁移，再以 Node.js 作为 PID 1 启动 HTTP 服务。迁移失败时应用不会启动。Compose 的 330 秒停止宽限用于让正在进行的有限 Provider、搜索和回复请求尽量完成；它只影响容器停止，不参与正常工作流执行，也不是工作流总时间预算。

## 首次部署

README 提供从空目录到首次回复的[完整快速流程](../README.md#10-分钟完成首次配置)。这里补充配置选择和生产要求。

### 推荐方式：Codex 辅助部署

BubblePilot 的部署同时涉及服务器网络、Docker、两套密码、五类随机 Secret、BlueBubbles REST/Webhook、HTTPS、聊天监听和可选 AI Provider。建议把仓库交给 Codex App 或 Codex CLI，并提供服务器的非敏感信息，让 Codex 先检查、规划、执行和验证。可直接复制的完整任务示例见 README 的[“提供服务器信息，让 Codex 协助部署”](../README.md#推荐提供服务器信息让-codex-协助部署)。

应提供的信息：

| 类别        | 示例                                                            | 是否可直接写入对话                        |
| ----------- | --------------------------------------------------------------- | ----------------------------------------- |
| 服务器      | OS、架构、SSH 主机/端口/用户、部署目录                          | 可以，但不要提供 SSH 私钥                 |
| 网络        | 对外域名、DNS 状态、反向代理、BlueBubbles 到 Webhook 的可达方式 | 可以                                      |
| 部署        | 源码构建或精确镜像、Docker/Compose 状态                         | 可以                                      |
| BlueBubbles | Server URL、发送方式、Chat GUID 是否已知                        | URL 按敏感信息处理；Password 不粘贴到对话 |
| 数据        | 保留天数、是否启用联网搜索、需要监听的聊天范围                  | 可以；真实聊天内容不要提供                |
| AI          | 接口类型、Base URL、模型、是否需要搜索                          | 可以；API Key 不粘贴到对话                |

Codex 应先报告阻塞项，再执行部署；随机 Secret 应直接写入权限受限的 `.env`，不要显示在回复或日志中。两套管理密码、BlueBubbles Password 和 AI Key 应由用户在受控终端输入或从服务器上的受控 Secret 来源读取。

无论是否使用 Codex，下列动作仍需要用户明确确认：

- 授权连接目标服务器和修改反向代理；
- 输入或读取真实凭据；
- 开启聊天监听和生产工作流；
- 执行导出、删除、恢复数据库或其他不可逆操作。

Codex 的完成报告至少应包含 Compose 校验、容器状态、`/health/ready`、BlueBubbles REST 结果、Webhook URL、尚需在 Web 页面完成的步骤和回滚方法。不要仅以“容器已启动”作为部署完成标准。

### 1. 准备 `.env`

```bash
cp .env.example .env
```

每个 `CHANGE_ME` 都必须替换。至少需要：

1. 相同的 `POSTGRES_PASSWORD` 和 `DATABASE_URL` 密码；推荐使用十六进制随机值，避免连接串转义问题。
2. 彼此独立的 `API_ACCESS_TOKEN`、`SETTINGS_ENCRYPTION_KEY`、`BLUEBUBBLES_WEBHOOK_SECRET` 和 `SEARXNG_SECRET`。
3. 两个不同明文密码生成的 `APP_LOGIN_PASSWORD_HASH` 和 `SENSITIVE_OPERATION_PASSWORD_HASH`。
4. 有效的 `BLUEBUBBLES_SERVER_URL` 和 `BLUEBUBBLES_ACCESS_TOKEN`。
5. 明确的消息正文保留期；默认 `MESSAGE_RETENTION_DAYS=90`。

生成随机值：

```bash
openssl rand -hex 32
```

使用项目容器生成 scrypt 哈希；运行两次：

```bash
printf '输入密码（输入不会显示）：' >&2
IFS= read -r -s BUBBLEPILOT_PLAIN_PASSWORD
printf '\n' >&2
printf '%s' "$BUBBLEPILOT_PLAIN_PASSWORD" | \
  docker compose run --rm --no-deps --build --entrypoint node app dist/app/hash-password.js
unset BUBBLEPILOT_PLAIN_PASSWORD
```

哈希包含 `$`，写入 `.env` 时必须使用单引号。登录密码只用于建立管理会话；敏感操作密码用于正文、监听、设置、审计、导出和人工恢复，两者不能复用。

`SETTINGS_ENCRYPTION_KEY` 加密 PostgreSQL 中的 BlueBubbles 和 AI 凭据，必须和数据库备份一起稳定保管。丢失后无法解密已有凭据，只能重新录入；升级时不要重新生成。

完整变量、范围和默认值见[接口与配置契约](接口与配置契约.md#必填运行时配置)。

### 2. 选择镜像方式

从当前源码构建：

```bash
docker compose up -d --build
```

使用已发布镜像：

```dotenv
BUBBLEPILOT_IMAGE=ghcr.io/shigella520/bubblepilot:X.Y.Z
```

```bash
docker compose pull app
docker compose up -d --no-build
```

正式环境固定不可移动的 `X.Y.Z`。`dev` 会被后续手动构建覆盖；需要验证特定提交时使用 `sha-<commit>`。私有 GHCR 镜像需要先用只含 `read:packages` 权限的凭据执行 `docker login ghcr.io`，不要把凭据写入 `.env`。

### 3. 启动检查

```bash
docker compose config
docker compose up -d --build
docker compose ps
curl --fail http://127.0.0.1:8080/health/live
curl --fail http://127.0.0.1:8080/health/ready
```

`live` 只表示进程可响应；`ready` 还要求 PostgreSQL 可查询且迁移成功。首次启动时应等待 `app`、`postgres` 和 `searxng` 均为 `healthy`。

不要执行 `docker compose down -v`，除非你明确要删除 PostgreSQL 持久卷和全部 BubblePilot 数据。普通停止使用 `docker compose down` 或 `docker compose stop`。

## 连接 BlueBubbles

### 1. 验证 REST 连接

登录 BubblePilot 后进入“设置”，完成敏感操作验证。确认：

- Server URL 是 BlueBubbles 根地址，不包含具体 API 路径；
- Access Token 是 BlueBubbles REST API Password；
- 发送方式为实例实际支持的 `private-api` 或 `apple-script`；
- 请求超时通常保持 30 秒。

同一区域还可以启用“链接卡片解析”和“公网 Open Graph 兜底”，并设置 1-15 秒的 OG 单次请求超时。解析优先读取 BlueBubbles 已生成的卡片；兜底仅访问通过公开地址校验的 HTTP/HTTPS 页面，不下载图片。关闭兜底不会影响 BlueBubbles 卡片解析，关闭总开关则新消息不再采集预览。

点击“验证服务连接”。它只读请求 BlueBubbles `/api/v1/server/info`，用于定位 URL、网络和 Token；成功不代表 Webhook 已经配置。

保存后的设置使用 `SETTINGS_ENCRYPTION_KEY` 加密写入 PostgreSQL并立即生效。页面不回显 Secret；留空表示保留当前值。数据库设置优先，`.env` 仍作为启动回退。

### 2. 配置 Webhook

在 BlueBubbles Server 新建 Webhook，订阅 `New Messages`：

```text
https://bubblepilot.example.com/api/v1/webhooks/bluebubbles?token=<BLUEBUBBLES_WEBHOOK_SECRET>
```

BlueBubbles 不附加自定义签名头，因此 Secret 只能放在 URL。反向代理必须关闭此路径查询串的访问日志。

排查顺序：

1. 从另一账号向测试聊天发送一条消息。
2. Dashboard 应出现新的入站事件；“消息”页应出现聊天元数据。
3. 若聊天未预先写入 `MONITORED_CHAT_IDS`，第一条消息只用于发现，不归档正文。
4. 完成二次验证并启用聊天监听，再发送第二条消息。
5. 第二条消息应显示 `archived`；相同事件重投应为 `duplicate`。

REST 验证成功但聊天始终不出现时，检查 Webhook URL、Secret、反向代理可达性、请求体限制和 BlueBubbles 投递日志。详细字段与错误分类见 [BlueBubbles 集成说明](BlueBubbles集成说明.md)。

## 配置 AI 与工作流

### AI Provider

在“AI Provider”页面：

1. 创建 Provider，选择 Chat Completions 或 Responses，填写 Base URL、模型、API Key 和超时；单次请求超时可设为 1-360 秒。多账号池网关若需要固定会话或 Responses 长前缀缓存，可将“会话亲和”设为“固定会话与缓存键”；系统会同时发送稳定 `X-Session-ID`，并为 Responses 发送同值 `prompt_cache_key`。其他 Provider 保持关闭。
2. 只按实际能力声明 Function Calling、托管搜索或原生图片输入，再运行连接测试并确认各项独立探测结果。
3. 创建 Provider 路由，设置候选固定顺序、Fallback、Node Retry、降级阈值和冷却时间。
4. 工作流只引用 Provider 路由，不直接保存 URL 或 Secret。

API Key 为只写字段，服务端加密保存；测试使用虚构输入，不读取聊天、不执行生产 Fallback，也不改变生产健康计数。

“执行与审计”页面顶部使用管理浏览器的本地时区展示每个 Provider 今日、本周、本月的 Token 和请求汇总，并以最近 1/6/12/24/48 小时折线观察 Token、请求和缓存命中。实时区域每 60 秒自动更新，页面不可见时暂停。缓存命中率是 Token 加权值，Provider 未返回缓存字段时显示“暂无数据”，不解释为 0% 命中。迁移 `0030_ai_provider_attempt_usage_index.sql` 只增加时间聚合索引，不改变已有 Attempt 数据。

### 联网搜索

默认关闭：

```dotenv
ENABLE_WEB_SEARCH=false
```

启用 SearXNG：

```dotenv
ENABLE_WEB_SEARCH=true
SEARXNG_SECRET=至少-32-字符的独立随机值
SEARXNG_ENGINES=
SEARXNG_LANGUAGE=zh-CN
```

修改后重启应用：

```bash
docker compose up -d
```

### 工作流上下文时区

归档消息和数据库时间始终以 UTC 存储。通过 IANA 时区配置工作流上下文、文本模板、AI 历史消息和压缩摘要中的时间展示：

```dotenv
TZ=Asia/Shanghai
```

BubblePilot 不维护单独的应用时区配置：若触发器显式配置了时间窗口时区，该次执行使用触发器时区；否则直接使用容器 `TZ`。修改后重启容器即可，既有归档数据无需迁移；摘要状态会按新时区建立独立语义版本，避免复用旧时区摘要。

### AI 请求结构追踪

请求结构追踪是长期启用的内置可观测能力，无需环境变量。“执行与审计”的 Provider Attempt 会并排显示请求共同前缀、仅尾部追加判断、配置与固定缓存键是否稳定，以及 Provider 实际缓存 Token 命中率；逐项角色、内容类型、字符数、图片计数、项目 Hash 和累计前缀 Hash 默认折叠。追踪不会保存聊天正文、API Key 或图片 Base64；跨请求比较基线保存在进程内，应用重启后的第一条请求显示“等待下一请求建立对比”。

AI 页面应显示 `searxng · 可用`。状态通过 `/healthz` 判断；单个引擎 CAPTCHA、零结果或暂时失败只会出现在实际工具轨迹，不代表整个后端宕机。

工作流联网策略：

| 策略       | 用途                                 |
| ---------- | ------------------------------------ |
| `disabled` | 摘要、改写和固定知识问答             |
| `auto`     | 普通 Bot，由模型判断是否需要实时资料 |
| `required` | 必须取得至少一条网页结果的流程       |

托管搜索探测通过时优先使用 Provider 能力；否则需要 Function Calling，由 AgentRunner 调用 SearXNG。来源可以完整、精简或隐藏，但管理端始终保留有限工具轨迹。

本地 SearXNG 搜索默认对每个查询策略最多尝试 2 次，每次独立使用 8 秒单请求超时。仅超时、连接失败和 HTTP 429/502/503/504 会重试；每次尝试都会写入工具轨迹。管理员在 AI 页面统一配置单个查询尝试次数、单次请求超时、退避、结果数量和搜索失败处理；设置保存在数据库并对新的执行立即生效，不需要修改 Compose 或重启容器。工作流节点不覆盖这些全局参数，也不再配置工具总预算。

“搜索失败处理”选择“自动模式降级，必须模式失败”时，`auto` 会在搜索重试耗尽后继续生成明确标注“未能联网核实”的降级回答，`required` 则保持严格失败。需要消息优先送达时可以选择“全部降级继续回答”；需要保证每个最新事实都有搜索依据时应选择“全部让 AI 节点失败”。迁移 `0021_ai_web_search_settings.sql` 只新增这张单例配置表，不修改现有工作流和执行数据。

### 原生图片输入

升级并完成迁移后，“AI Provider”页面会出现原生图片能力声明、独立探测结果和全局“原生图片输入”配置。该功能默认关闭；先为确实支持图片的 Provider 勾选能力并运行测试，看到“已验证”后，再打开全局开关。启用后所有 AI 节点自动尝试读取当前图片，开启“包含已加载聊天上下文”的节点还会读取配置数量内的最近历史图片，不需要修改工作流定义。

建议从默认的当前附件 4 张、历史 2 张、总计 6 张、单图 10 MiB、合计 20 MiB 和 15 秒获取超时开始。图片详情等级会直接影响 Provider Token 和延迟。下载、格式校验或视觉 Provider 不可用时，执行自动降级为文本回答，不让整个工作流失败；在执行详情的“图片输入”轨迹检查来源、状态、MIME、字节、耗时、主机名和错误码。迁移 `0024_ai_image_input.sql` 新增全局设置与脱敏诊断表并扩展 Provider 能力 JSON，`0026_ai_trusted_image_hosts.sql` 为设置表追加可信图片域名。

若图片轨迹为 `AI_IMAGE_BLOCKED_ADDRESS`，先检查主机 DNS。公开域名在代理环境中解析为 `198.18.0.0/15` Fake-IP 时，可以把该精确域名加入“可信链接图片域名”；不要填写 URL、端口、路径或通配符。该配置只豁免 Fake-IP，不能访问真实局域网或回环地址。域名不由自己控制或来源不明确时不要加入白名单。

迁移 `0033_message_image_summaries.sql` 增加图片摘要任务、状态和 AI Attempt 用途。无需增加环境变量或节点配置；新入库图片自动异步处理，旧图片不会批量回填。消息搜索中的“图片与 AI 摘要”弹窗展示图片预览、摘要状态、Provider、模型、耗时和错误码；图片预览由服务端代理，不返回 BlueBubbles 凭据或原始附件地址。`pending` 长期不推进时检查是否存在启用且图片能力探测为“已验证”的路由；`unavailable` 通常表示附件或卡片主图已经无法下载；`failed` 表示 Provider 或输出校验失败。任务失败不会让消息工作流失败，应用重启会依据数据库租约恢复。消息保留任务会同步清除摘要正文，数据库备份验证也必须包含 `message_image_summaries`。

### 第一条工作流

最小固定回复：

```text
消息触发器 → 回复消息 → 结束
```

最小 AI 回复：

```text
消息触发器 → 加载聊天上下文 → AI 对话 → 回复消息 → 结束
```

需要让 AI 识别群聊成员时，先在“消息 → 聊天监听配置”中点击目标聊天的“成员映射”，为历史出现的发送者 ID 填写本名和昵称。加载聊天上下文动作会自动提取本次窗口涉及的映射，AI 对话自动应用身份识别规则，无需把全量名单写进提示词。固定背景、当前消息或上游动作输出的文本组合仍使用“渲染文本”。

聊天摘要由系统统一配置并按聊天后台维护，不再在“加载聊天上下文”中单独开启或选择 Provider。消息归档后按全局 `baseMessageWindow`（基础窗口）、`redundancyMessageWindow`（冗余窗口）、`characterLimit` 和 `includeFromMe` 检查；未压缩消息数包含当前归档消息，达到基础窗口与冗余窗口之和时并行创建摘要压缩任务和工作流任务。摘要任务固定压缩摘要游标之后最早的冗余窗口消息；工作流不等待压缩，按触发消息游标读取已提交摘要和其后的全部原始增量。上下文提取阶段超过目标字符数时从较早消息开始舍弃完整消息，不截断单条消息；该限制不约束下游 AI 对话拼接后的整体请求。摘要未完成或失败时继续使用上一版摘要，同一次执行不切换快照。执行详情显示本次读取的摘要版本和消息水位线；“执行与审计”中的独立“对话压缩”区块显示压缩操作状态、原因、范围、耗时、Token、游标和错误码，但不保存完整聊天正文。Provider 的真实 Prompt Cache 必须查看 Attempt 中的 `cachedPromptTokens`，不能用摘要状态缓存判断。

多个 AI 串联时，让第一个负责理解对话的 AI 开启“包含已加载聊天上下文”；后续只做润色、格式化或审核的 AI 关闭该开关，并连接前一个 AI 的输出。后续输入会标记为 `<upstream_input>`，不会再次附带聊天历史和成员信息。若后续 AI 也需要核对原始发言人和聊天事实，再显式开启该开关。

带 iMessage 链接卡片的新消息会在“消息”详情显示解析状态、标题、摘要、来源和有限诊断。AI 读取当前消息或已加载历史时自动获得这些不可信元数据；启用原生图片输入且 Provider 探测通过时，还可读取卡片主图。卡片本身不代表已读取网页全文，需要最新或完整内容时仍应启用联网搜索。解析失败不会中断工作流，可先根据诊断区分 BlueBubbles 空载荷、连接/超时和 Open Graph 安全拦截。

“消息触发器”必须选择已监听聊天并显式启用；工作流保存后还要点击顶部“启用”。测试消息到达后，在“执行”页面确认入站判定、节点、Provider Attempt、工具轨迹和出站状态。

## 反向代理与安全

生产环境只公开反向代理，不公开 PostgreSQL 和 SearXNG。反向代理应：

- 为 Web 管理端和 Webhook 提供 HTTPS；
- 转发 `Host` 和 `X-Forwarded-Proto`；
- 不缓存管理 API 和导出下载；
- 不记录 Webhook 查询串或响应正文；
- 对 `/api/v1/exports/*/download` 保留 `Cache-Control: no-store`；
- 保持 Webhook 请求体上限与 `WEBHOOK_BODY_LIMIT_BYTES` 一致。

`SESSION_COOKIE_SECURE`：

- `auto`：默认；根据 HTTPS 或 `X-Forwarded-Proto: https` 添加 `Secure`；
- `true`：始终添加，只用于浏览器一定通过 HTTPS 的部署；
- `false`：仅用于受控纯 HTTP 内网测试。

无论该设置如何，Cookie 始终为 `HttpOnly` 和 `SameSite=Strict`。

运行数据均按敏感信息处理：`.env`、PostgreSQL 备份、导出、工作流、执行轨迹和日志必须限制访问。真实消息、Token、Prompt 或数据库导出不得上传到 Issue、截图或测试 Fixture。

## 健康、日志与诊断

```bash
docker compose ps
docker compose logs --tail=200 app
docker compose logs --tail=200 postgres
docker compose logs --tail=200 searxng
scripts/diagnose.sh
```

若要让诊断脚本读取脱敏运行状态，只在当前 Shell 临时设置 Token：

```bash
export BUBBLEPILOT_API_ACCESS_TOKEN='虚构示例，实际请从安全位置读取'
scripts/diagnose.sh
unset BUBBLEPILOT_API_ACCESS_TOKEN
```

脚本不会自行读取或打印 `.env` Token。普通日志只记录 `correlationId`、实体 ID、状态和错误码。

常见问题：

| 现象                          | 优先检查                                                          |
| ----------------------------- | ----------------------------------------------------------------- |
| `ready` 返回 503              | PostgreSQL 健康、连接串、迁移日志                                 |
| BlueBubbles REST 成功但无聊天 | Webhook URL/Secret、反代可达性、BlueBubbles 投递日志              |
| 聊天出现但没有正文            | 该聊天是否已启用监听；首次发现消息不会回填                        |
| 消息归档但无执行              | `automationOutcome`、触发器节点与工作流是否都启用                 |
| AI 调用失败                   | Provider 基础测试、路由有效候选、Attempt 错误码                   |
| 搜索失败                      | 实例总开关、SearXNG 健康、Function Calling/托管搜索能力、工具轨迹 |
| 回复为 `unknown`              | 先在 BlueBubbles 确认最终结果，不直接重发                         |
| 内容不再可见                  | `contentRedactedAt` 和 `MESSAGE_RETENTION_DAYS`                   |

消息保留任务在应用就绪后运行，之后每小时最多处理 10,000 条。`MESSAGE_RETENTION_FAILED` 表示最近一次任务失败；`MESSAGE_RETENTION_BACKLOG` 表示本批达到上限，需观察后续批次是否下降。

## 失败执行处理

自动恢复和人工恢复都不能破坏出站幂等：

- `retrying` 在 `nextRetryAt` 未超过 `STALE_RETRY_SECONDS` 前等待自动执行；
- `failed`、`dead-lettered` 和逾期 `retrying` 可以在二次验证后人工恢复；
- 恢复创建关联的新执行，不修改源执行；
- `sending`、`unknown` 或 `confirmed` 出站记录禁止人工重试；
- 人工关闭保留节点、Provider、工具和发送轨迹，并写入审计。

不要通过手工改库、删除幂等记录或直接重放请求绕过服务端检查。

## 备份与恢复

创建权限为当前用户私有的 PostgreSQL custom-format 备份和 SHA-256 文件：

```bash
scripts/backup-postgres.sh
```

将备份恢复到同一 PostgreSQL 容器内的随机临时数据库，检查迁移和关键表，最后自动删除临时库：

```bash
scripts/verify-postgres-backup.sh backups/bubblepilot-YYYYMMDDTHHMMSSZ.dump
```

校验脚本先验证同名 `.sha256`，只删除自己创建且通过固定前缀检查的临时数据库，不覆盖生产库。备份和校验和必须复制到受控异机位置；`.env` 或 Secret 不要与未加密数据库备份放在同一无保护位置。

定期恢复演练至少确认：迁移版本、Chat 监听与成员映射、工作流发布状态、触发器、Provider/路由元数据、执行轨迹、出站幂等和审计记录。记录模板见[验收与演练](验收与演练.md)。

## 升级与回滚

### 从 1.0.0 升级到 1.1.0

1.1.0 增加 Agent 联网搜索全局配置、聊天成员身份、链接卡片和原生图片输入。迁移 `0021` 至 `0026` 均为追加式变更，不修改已发布工作流定义，也不新增必填环境变量。升级前仍必须备份 PostgreSQL，并保持原有 `SETTINGS_ENCRYPTION_KEY`、两套密码哈希和 BlueBubbles Secret 不变。

升级后先确认迁移完成和 `/health/ready` 正常，再依次验证 SearXNG、Provider Function Calling 与图片输入能力。联网搜索仍受部署级 `ENABLE_WEB_SEARCH` 总开关控制；原生图片输入默认关闭，需要在 AI 页面确认至少一个 Provider 的图片能力为“已验证”后手动启用。回滚到 1.0.0 前必须恢复升级前数据库备份，旧应用不能安全解释新增表和消息信封字段。

### 从 1.1.0 升级到 1.2.0

1.2.0 增加增量上下文摘要、Provider 会话亲和、AI 用量与 Prompt Cache 诊断，并稳定历史消息、图片和链接预览的请求前缀。迁移 `0026` 至 `0030` 均为追加式变更，涉及受信任图片域名、会话摘要、请求诊断、会话亲和和用量查询索引；不修改已发布工作流定义，也不新增必填环境变量。

升级后确认 `/health/ready` 正常，并通过连续对话验证摘要、图片输入、Token 用量和缓存诊断。需要多账号池黏性的兼容 Provider 可在 AI 页面启用会话亲和；普通 Provider 无需调整。部署环境建议使用标准 `TZ` 统一管理端与 AI 上下文时间。回滚到 1.1.0 前应恢复升级前数据库备份，不要让旧应用长期运行在已完成 1.2 迁移的数据库上。

### 聊天级摘要窗口升级

后续版本中的迁移 `0037`–`0039` 将摘要状态收敛到聊天级，并把全局配置字段更新为 `baseMessageWindow`、`redundancyMessageWindow` 和 `characterLimit`。升级前备份 PostgreSQL；迁移会回填窗口值、建立摘要 revision 与后台压缩轨迹，并清理旧工作流节点中的摘要字段。被标记为“需要重新保存”的旧工作流必须在工作流页面保存为新版本后才能重新发布。升级后在 AI 设置页确认全局摘要 Provider 与消息窗口，在“执行与审计”的“对话压缩”区块检查任务状态；摘要 Worker 运行在现有 Node 进程内，不需要额外服务或进程。

### 通用升级步骤

升级前：

1. 阅读 Release Notes，检查迁移、环境变量、认证和数据保留变化。
2. 创建备份并完成临时库恢复校验。
3. 准备上一精确版本镜像和回滚决定。
4. 运行：

```bash
scripts/preflight-upgrade.sh backups/bubblepilot-YYYYMMDDTHHMMSSZ.dump
```

将 `BUBBLEPILOT_IMAGE` 改为目标精确版本：

```bash
docker compose pull app
docker compose up -d --no-build
docker compose ps
curl --fail http://127.0.0.1:8080/health/ready
```

随后验证登录、BlueBubbles REST、测试聊天入站、工作流回复、执行详情和搜索后端（若启用）。

数据库迁移只前向执行。把应用镜像切回旧版本不会回滚数据库；若新迁移与旧应用不兼容，只能按 Release Notes 恢复升级前数据库备份。不要重写迁移历史表，也不要在没有备份的情况下手工回滚 Schema。
