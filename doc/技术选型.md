# BubblePilot 技术选型

本文记录 BubblePilot 当前已落地的技术栈、选择理由、约束和重新评估条件。具体版本以 `package.json`、`pnpm-lock.yaml`、`Dockerfile` 和 `compose.yaml` 为准；架构边界见[概要设计](概要设计.md)，开发命令见[开发指南](开发指南.md)。

## 1. 选型结论

BubblePilot 后端采用 Node.js + TypeScript 模块化单体，使用 Fastify 提供 HTTP API，PostgreSQL 保存配置、幂等、归档和执行事实。默认通过 Docker Compose 单机部署，后续执行队列和 Worker 仍通过接口隔离。

| 层面 | 当前选型 | 版本基线 | 用途 |
| --- | --- | --- | --- |
| 运行时 | Node.js | 22+ | HTTP、异步 I/O 和应用运行时 |
| 语言 | TypeScript、ESM、严格模式 | 5.x | 领域模型、适配器和应用代码 |
| 包管理 | pnpm | 11.x | 锁定依赖和受控构建脚本 |
| HTTP | Fastify | 5.x | Webhook、健康检查和管理 API |
| 数据库 | PostgreSQL | 16 | 归档、幂等、配置和执行权威数据 |
| 数据访问 | `pg` + 显式 SQL | 8.x | 事务、唯一约束和分页查询 |
| 数据迁移 | 只追加 SQL 迁移 | 仓库内实现 | Schema 版本和启动迁移 |
| 运行时校验 | Zod | 4.x | 环境变量、Webhook 和 API 参数 |
| 接口合同 | OpenAPI、JSON Schema | OpenAPI 3.1、Draft 2020-12 | HTTP 与消息信封机器合同 |
| 测试 | Vitest、Fastify `inject` | 3.x | 单元、API 和 PostgreSQL 集成测试 |
| 质量工具 | ESLint、Prettier、TypeScript | 锁文件固定 | 静态检查、格式和生产构建 |
| 部署 | Docker、Docker Compose | Compose v2 | 单机自托管与依赖编排 |
| CI/CD | GitHub Actions、GHCR | 仓库工作流 | 迁移、测试、镜像试构建、Dev 与正式镜像发布 |

大版本表达的是兼容基线，补丁版本由 `pnpm-lock.yaml` 固定，不在说明文档中重复维护。

## 2. 选择原则

技术选择按以下顺序权衡：

1. 消息接入、数据库、BlueBubbles REST 和 AI Provider 都是 I/O 密集任务，优先考虑异步 I/O 和可维护性，而不是极限 CPU 性能。
2. 消息信封、工作流、节点配置和 API 大量使用 JSON，需要低成本维护类型、Schema 和运行时校验。
3. 项目采用短期功能分支和垂直切片，需要较少样板代码并能快速建立测试闭环。
4. 默认运行在个人或小型服务器上，单机部署必须简单；分布式能力通过接口演进，不提前引入基础设施。
5. Web 管理端将在后续实现，TypeScript 生态有利于共享 API 和工作流合同，但不要求前后端直接共享内部领域类型。

## 3. 为什么使用 Node.js + TypeScript

### 3.1 与负载模型匹配

典型链路为：

```text
Webhook → PostgreSQL → Trigger / Workflow → AI API → BlueBubbles REST
```

主要耗时来自网络和数据库等待。Node.js 的事件循环可以高效处理这类并发，不需要为当前吞吐提前承担多线程服务或系统语言的复杂度。

### 3.2 适合版本化合同和配置图

TypeScript 适合表达消息信封、节点联合类型和工作流配置；Zod 和 JSON Schema 负责运行时边界，避免把编译期类型误当作生产输入校验。OpenAPI 则作为前后端和外部调用方的 HTTP 权威合同。

### 3.3 迭代与 Web 协同成本较低

Fastify 的依赖注入和 `inject` 测试可以快速完成一个垂直切片。未来 Web 管理端无论选择 Vue 还是 React，都可以从 OpenAPI 和工作流 Schema 生成 TypeScript 类型，减少两套模型漂移。

### 3.4 已知约束

- CPU 密集节点不能长时间占用事件循环，应迁移到 Worker Thread、独立 Worker 或专用服务。
- TypeScript 类型在运行时不存在，所有外部输入必须继续使用 Zod 或 JSON Schema 校验。
- Node.js 依赖数量通常多于 Go/Rust，因此必须保留锁文件、构建白名单、依赖审计和 CI。
- 单进程不是可靠队列；M2 的执行传输层必须维持接口边界，为未来持久队列保留替换点。

## 4. Java、Go 与 Rust 对比

| 方案 | 主要优势 | 对当前项目的主要成本 | 更适合采用的情形 |
| --- | --- | --- | --- |
| Java | Spring 生态、事务、安全、监控和大型团队经验成熟 | JVM 和镜像较重；工作流 JSON、DTO 和映射样板较多 | 企业多租户、复杂 RBAC、OIDC/LDAP、大型 Java 团队 |
| Go | 单一二进制、启动快、内存低、Goroutine 适合并发 Worker | 复杂联合类型、动态节点配置和 JSON 校验代码更机械 | 极简部署、低资源、大量并发 Worker 成为第一优先级 |
| Rust | 性能、内存安全和资源利用率最好 | 开发与编译成本高；异步和动态工作流建模更复杂 | 高吞吐网关、不可信二进制协议、严格资源约束或 CPU 密集处理 |

这些语言不是被永久排除。供应商适配器、执行传输层和节点合同保持边界后，可以在有明确收益时用其他语言实现独立 Worker，而不重写 BubblePilot 的领域语义。

## 5. 暂缓的技术决策

| 能力 | 决策时间 | 当前约束 |
| --- | --- | --- |
| Web 前端框架 | M4 | 在工作流编辑与搜索交互明确后比较 Vue 和 React |
| 进程内队列实现 | M2 | 先定义执行传输接口、状态与幂等，再选择具体库 |
| 外部持久队列 | M5 或明确负载出现时 | 不提前引入 Redis、RabbitMQ、NATS 或 Kafka |
| AI SDK | M3 | 先定义 OpenAI 兼容 Provider 合同，不让节点绑定厂商 SDK |
| 登录与会话库 | M4 | 必须支持服务端会话、二次验证和审计 |
| ORM/查询构建器 | 查询复杂度出现明确痛点时 | M1 继续使用 `pg` 和显式 SQL，迁移保持纯 SQL |

## 6. 重新评估条件

出现以下情况时，应通过独立 ADR 或设计 PR 重新比较技术方案：

- CPU 密集处理持续阻塞事件循环，独立 Worker 仍不能满足延迟目标；
- 单实例吞吐、故障隔离或任务持久性要求必须引入外部队列；
- 容器内存和启动时间成为实际部署瓶颈；
- 团队主要维护语言或运维平台发生变化；
- 多租户、企业认证和权限模型显著超出当前单实例管理员范围；
- 显式 SQL 在复杂搜索和工作流查询中产生可量化的维护问题。

技术栈变更必须同时更新本文、开发指南、概要设计、CI、部署文件和迁移策略，不能只替换框架代码。
