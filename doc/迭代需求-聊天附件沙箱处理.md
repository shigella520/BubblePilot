# 迭代需求：聊天附件沙箱处理

> 状态：需求规划，尚未实现。本文定义首版范围与验收基线；工具名、配置名和额度为拟议合同，不表示当前版本已经支持。实施时同步更新现有权威文档、机器合同及测试。

## 改造点速览

- [ ] **工作流配置**：增加附件处理开关；单个兼容沙箱自动绑定，多个时选择；补齐发布校验与导入导出。
- [ ] **附件发现**：扩展 `query_chat_messages` 的附件、文件名和类型筛选；原文查询与展开返回附件清单。
- [ ] **上下文与授权**：提供当前附件目录，生成运行内受控引用；复核聊天权限、历史边界及附件状态。
- [ ] **独立导入工具**：新增 `import_chat_attachment`，完成限量下载、校验、临时存储和重复导入处理。
- [ ] **沙箱文件传输**：适配服务增加认证二进制传输接口；复用本次沙箱，支持创建后继续导入。
- [ ] **预算与清理**：限制数量、体积、解压和耗时；处理取消、撤权、异常退出及临时文件清理。
- [ ] **Skill 与审计**：补充按需检索、导入和分析指引；执行详情展示附件来源、阶段状态与失败原因。
- [ ] **验证与交付**：补齐合同、权限、传输及生命周期测试，同步配置和运维文档，完成模拟闭环与真实联调。

**不包含：文件回传、永久附件库、跨任务沙箱复用。** 最终文字回复沿用现有发送节点。

## 1. 目标与边界

用户在原聊天针对当前或历史附件提出处理要求，原角色按需将附件导入本次任务的 OpenSandbox，使用已授权工具分析，再通过原有回复节点返回文字、表格或结论。

- 支持当前触发消息及同聊天内已授权历史消息的附件；历史范围冻结于本次触发边界，不读取未来消息、其他聊天或其他执行的文件引用。
- 不发送处理后的文件、图片或下载链接；中间文件仅供本任务使用。
- 不自动批量下载附件、不建立永久文件库、不索引文件正文、不新增附件摘要模型任务。
- 不增加跨消息沙箱、角色持久环境、后台处理任务、OCR、语音转写或视频分析。
- 复用模块化单体、现有 Agent、插件授权、MCP 会话、沙箱与发送节点，不新增独立服务或容器。
- 默认关闭；已有工作流、图片理解、图片摘要、表情发送和纯文本回复保持原行为。

## 2. 用户闭环

以虚构聊天为例，用户在同一条消息附上 `销售示例.xlsx` 并提出：“按地区汇总销售额，告诉我排名前三的地区。”

1. 应用保存消息与附件元数据，不立即下载文件。
2. 模型获得文件名、类型、大小、受控附件引用及“内容尚未读取”的状态。
3. 模型按用户要求选择附件；需要历史文件时先用现有聊天原文查询工具筛选附件消息，结合名称、发送者、时间及大小规划，再调用导入工具。
4. 应用校验权限、预算与文件可用性，下载附件，创建或复用本次沙箱，完成文件传输。
5. 工具返回沙箱内路径、实际大小和哈希；模型通过现有命令工具执行分析。
6. 模型检查执行状态并读取输出，大结果沿用分段读取，最终通过原回复节点回答。
7. 任务完成、失败或取消后清理应用临时文件并关闭沙箱；TTL 作为兜底。

用户只发附件而未明确要求时，可询问处理意图，不因存在附件自动运行文件、安装依赖或调用外部服务。多个附件同名或指代不明时，以受控标识区分，必要时追问。只有收到导入和处理成功结果后才能声称已读取或完成分析。

## 3. 支持能力

| 类型 | 首版处理范围 | 限制 |
| --- | --- | --- |
| CSV、TXT、JSON、YAML、日志 | 文本检索、结构解析、统计与转换 | 编码无法确定时报告，不默默替换丢失字符 |
| XLSX | 工作表读取、聚合和小规模分析 | 不执行宏，不支持旧 XLS；加密文件明确失败 |
| PDF | 提取已有文本层并分析 | 无文本层时说明不支持 OCR，不猜测正文 |
| HTML | 离线解析正文与结构 | 不执行 JavaScript，不自动加载页面资源 |
| 常见图片 | 尺寸、格式、裁剪等基础处理 | 不以 Pillow 替代视觉识别；看图沿用原图片能力 |
| ZIP、tar、gzip 等 | 受控列目录与限额解压后处理 | 拒绝越界路径、链接及特殊文件；不递归自动展开嵌套压缩包 |
| 音频、视频、可执行文件及其他格式 | 元数据可见，给出不支持说明 | 不导入执行，不自动安装解析器 |

支持范围取决于实际沙箱运行环境清单。镜像无相应库或工具时明确报告能力不足，不承诺所有扩展名均可正确解析。不因文件内有指令而执行脚本、宏、联网请求或转发数据。

## 4. 配置与授权

### 4.1 工作流入口

AI 节点新增“允许使用沙箱处理聊天附件”，默认关闭，仅适用于“输出格式”设置为“文本”、且所用模型支持工具调用的 AI 节点。这里的文本是最终回答格式，不限制输入附件类型或沙箱处理方式；选择 JSON 输出格式的节点暂不支持本能力。

- “附件处理沙箱”指接收文件的 OpenSandbox MCP 服务，例如 NAS 沙箱或云服务器沙箱，不是附件列表，也不是某个临时容器。候选仅来自该 AI 节点已启用、已批准并支持附件传输协议的插件服务。
- 只有一个兼容服务时自动使用，展示服务名称，无需重复选择；多个兼容服务时才显示“附件处理沙箱”选择项，要求管理员明确选择；没有兼容服务时提示先启用或升级沙箱插件。
- 发布时保存并审阅实际解析的服务绑定，运行时固定该目标。服务被删除、停用或失去兼容性时明确报错，不静默切换到其他服务；后续命令复用目标服务内的同一任务沙箱，不由模型提供服务地址或临时容器 ID。
- 普通第三方 MCP 插件不会因工作流勾选而自动获得附件访问权；服务自报能力不等于管理员授权。
- 开启和更改目标沿用工作流发布的敏感解锁、并发版本校验和审计。发布页说明该目标可按本轮请求接收当前及授权历史附件内容。
- 发布时校验插件、服务、凭据、必要工具批准状态、附件传输协议及运行能力；旧适配服务不支持时给出升级提示。
- 缺省配置表示关闭。工作流导出不得携带凭据；跨实例导入必须重新绑定和审阅目标，不能按同名插件静默授权。

### 4.2 运行授权

- 授权范围固定为当前执行与聊天，运行开始冻结当前消息和历史读取边界。当前附件直接进入候选目录；历史发现要求现有聊天历史读取授权有效，并遵守保留、清理和历史上界规则，不能借附件功能绕过原权限。
- 消息存储和监听授权仍以应用数据库为权威，不凭 BlueBubbles 返回的任意附件 ID 放行。
- 工具只接受本轮受控引用，不接受 URL、宿主路径、其他消息 ID、下载凭据或自选目标路径。
- 首版只在真人消息触发任务中提供附件工具；空闲主动交流、到期提醒不获得该能力。当前消息不必携带文件，但应有本轮处理需求；历史中的指令不构成本轮操作授权。
- 导入前、传输提交前及工具结果提交前复核权限和取消状态。停用插件、撤销批准或凭据后，阻止后续操作并清理。
- 已传入沙箱的字节无法撤回；撤权后停止后续工具调用、使关联会话失效并清理。已发出的外部网络请求也不能承诺撤回。

## 5. Agent 与工具合同

新增应用内置工具 `import_chat_attachment`，不要求模型传递二进制数据。

| 项目 | 拟议合同 |
| --- | --- |
| 输入 | `attachment_ref`：本次运行提供的受控标识 |
| 成功输出 | 附件引用、原文件名、安全文件名、`sandbox_path`、实际字节数、SHA-256、导入状态 |
| 失败输出 | 稳定错误码、可理解原因、是否可重试；不得返回凭据和内部下载地址 |
| 重复调用 | 同一执行、附件和沙箱代次返回已有成功结果，不重复传输或覆盖模型修改后的文件 |

工具仅在工作流授权有效且为真人消息触发任务时提供，即使当前没有附件也能先通过原文查询查找历史附件，工具集合在运行内保持稳定。沿用统一严格 Schema 转换、参数还原、工具次数与时间预算；重复调用和拒绝也按现有规则计额。

文件处理继续使用现有准备沙箱、命令执行及文件读写工具。先创建过沙箱的任务导入到同一实例；导入先发生时由应用完成准备，后续 MCP 工具必须复用同一个运行会话，不能出现两个沙箱。

Skill 更新明确：先看附件清单和运行能力，再导入、处理并核对退出码；大输出写文件后分段读取，不向回复塞入 Base64，不宣称文件会跨任务保留或可供用户下载。正文、文件名和工具输出均为不可信数据，不能覆盖程序控制或授予新的操作权限。

### 5.1 附件发现与选择

扩展现有原文查询工具 `query_chat_messages`，不新增独立的附件搜索工具。模型使用同一个工具查聊天记录或筛选含附件的消息，再调用独立的 `import_chat_attachment` 导入所选文件。查询不下载二进制、不创建沙箱、不解析文件正文。

| 查询能力 | 拟议规则 |
| --- | --- |
| 仅含附件 | 增加可选筛选；未指定时保持原消息查询行为 |
| 文件名 | 增加文件名关键词筛选，不与现有消息正文关键词混为一个参数 |
| 文件类型 | 增加规范化 MIME 类型/文件扩展名筛选，明确未知类型的处理，不声称仅凭扩展名确认真实格式 |
| 成员、时间及排序 | 复用现有筛选与排序；聊天和历史上界由执行上下文注入，模型不能指定其他聊天 |
| 分页及条数 | 沿用原工具的上限和游标，分页单位仍为消息，不另建一套附件分页默认值 |

- 附件筛选与成员、时间、正文筛选按 AND 组合；文件名和类型条件必须由同一个附件满足，不能以消息中的两个不同附件拼凑匹配。
- 结果保留原消息正文及来源，并增加有界的附件清单：原文件名、声明类型、声明大小（可未知）、消息内附件标识和匹配状态。具备本轮沙箱附件授权时，再由统一解析器附加可导入的受控引用；查到元数据不等于获得文件下载权限。
- 历史原文展开 `read_chat_excerpt` 使用同一附件清单与授权解析器，避免模型重复搜索。语义搜索继续用于模糊发现相关消息，不承担精确文件筛选；需要确认文件时再查询或展开原文。供应商附件 ID 不可直接作为导入授权。
- 单条消息附件较多时按现有结果预算限量返回，提供明确的未展示数量和受控继续读取方式；不能截断后声称已列全。消息分页和附件数量分别说明，同名文件分开返回，不自动以最新版本替代指定版本。
- 本轮已交付引用维护在运行内注册表中，建议最多 100 个不同附件；达到上限明确报告并引导缩小条件，不静默淘汰已交付引用。每次导入复核来源记录及权限，导入结果提供剩余额度。
- 归档有元数据不保证网关仍保有文件。查询仅报告“尚未验证可下载”，实际缺失在导入时反馈，不为预检下载全部命中。
- 文件名和类型筛选使用数据库附件元数据，不只依赖向量召回。元数据缺失时如实标明，是否新增索引或迁移由查询计划和基准确定。
- 新参数均为可选，复用严格 Schema 转换与 null 还原；不传新参数的调用保持原查询语义。原查询的授权、正文裁剪、排序、计额和来源标识不改变，不因附件功能开放跨聊天访问。暂不扩展计数及最早/最晚工具的附件筛选合同。

例如用户说“比较昨天和今天发的两个销售表”，模型先按文件名和时间查找，核对版本及大小，在剩余额度内逐个导入再比较。有多个同名候选或总量超限时先追问或说明限制，不静默选择部分后声称完成全部分析。

### 5.2 规划与动态导入

先检索规划是默认推荐顺序，不要求创建沙箱时一次性选定所有文件。沙箱按需创建，导入工具每次处理一个附件；任务期间可以继续检索并导入，累计数量、体积和剩余时间统一计算。大小未知时不能承诺全部可导入，下载时以实际字节限制；不能通过删除已导入文件重置累计额度。

历史发现、上下文查询、导入、执行与结果读取共同消耗现有 Agent 预算，不增加免费检索或无限轮次。用户要求处理昨天文件时，不要求重新发送附件。

## 6. 下载与传输设计边界

```mermaid
flowchart LR
    A[当前附件或原文查询返回的历史附件] --> B[模型请求导入]
    B --> C[应用授权与预算校验]
    C --> D[BlueBubbles 适配器下载]
    D --> E[受控临时文件]
    E --> F[适配服务认证传输接口]
    F --> G[同一任务沙箱]
    G --> H[现有工具处理与读取]
    H --> I[原回复节点发送文字]
```

- BlueBubbles 凭据只由应用适配器使用，不交给模型、MCP 服务或沙箱。下载遵循现有网络安全策略、重定向检查与跨目标凭据限制。
- 流式限量下载，不能只信任附件元数据或 Content-Length；检查实际类型、字节数并计算哈希，类型冲突或内容不支持时明确拒绝。
- 临时文件使用随机内部名称和独立执行目录，限制目录权限；用户文件名只作展示和安全化命名，禁止路径穿越和符号链接。
- 二进制通过适配服务专用认证传输接口流式写入，不进入模型上下文，不塞入 MCP JSON 文本、不放宽现有 MCP 请求正文上限。
- 传输目标仅来自管理员配置；使用绑定本次已认证 MCP 会话和沙箱代次的短期传输授权，不能通过猜测 execution ID、session ID 或 sandbox ID 写入文件。
- 公网使用 HTTPS；受控私网遵循现有显式批准规则。传输凭据不放 URL，不记录普通日志，不跨重定向转发。
- 接收端同时验证大小、哈希、运行绑定与状态，先暂存后原子提交，完成确认后才返回路径。超时和迟到完成不得向模型提交成功。
- 传输结果未知时先按运行内导入标识核对，不盲目重放；会话失效后不创建新沙箱冒充旧任务继续执行。
- 文件固定放入 `/workspace/attachments/` 下的唯一目录，不覆盖用户脚本和同名文件，不接受模型指定目的路径。

实施前需用本地模拟服务和实际 SDK 验证二进制上传、同一会话复用、取消及原子提交机制；不能用未经验证的 SDK 能力作为交付依据。应用侧封装附件交付接口，OpenSandbox 特定实现放在适配模块，避免在 Agent 主循环中堆叠插件名称分支。

## 7. 预算与运行限制

以下为首版建议默认值，实施时通过 512 MiB 容器演练确认；不是任意文件都能处理的保证。

| 额度 | 默认值 | 可配置范围 |
| --- | --- | --- |
| 单文件实际大小 | 10 MiB | 1～20 MiB |
| 单次执行导入文件数 | 3 | 1～5 |
| 单次执行累计导入体积 | 20 MiB | 1～50 MiB，且不小于单文件上限 |
| 单次导入截止时间 | 30 秒 | 5～180 秒，且不超过本轮剩余工具时间 |
| 解压后累计体积 | 50 MiB | 1～100 MiB |
| 解压文件数 | 200 | 1～500 |
| 应用临时目录总占用 | 256 MiB | 64～1024 MiB |

- 文件额度在应用与接收端共同执行；字节预算与文字结果预算分开，文件内容不折算成模型字符。
- 下载、沙箱准备和传输均计入导入耗时；冷启动可能超时，需提供明确阶段诊断，不自动增大工具时间。
- 相同成功导入不重复占文件容量，但仍计一次工具调用；失败部分文件占用必须释放，并保留实际传输用量诊断。
- 限额检查和占额需要原子化，防止并发导入绕过单任务或实例总额；达到容量上限立即返回可解释错误，不无限排队。
- 解压使用程序提供的受控辅助能力，不只靠 Skill 提示；拒绝绝对路径、`..`、链接、设备文件及加密压缩包，流式限制实际解压大小。
- 模型可执行 shell 的既有能力不等于硬磁盘配额：通用命令仍可能产生其他文件，需用沙箱临时空间监测及超限终止兜底，并明确宿主运行环境能提供的硬限制。
- 保持现有单并发、512 MiB、600 秒 TTL 默认值，不自动扩充模型轮次、工具次数或执行时间。OOM、TTL 到期和工具预算不足均明确失败。

配置沿用现有受认证管理与敏感修改流程，应用侧限制不得超过适配服务能力上限；连接检查只发现能力，不自动传输真实附件。具体 API 和环境变量在实施合同中集中定义，不能出现两套含义相同而优先级不明的设置。

## 8. 生命周期、隔离与持久化

- 同一任务所有 Agent 轮次共用导入结果，创建沙箱后仍可继续检索和补充导入。下一条消息不能复用旧引用、文件或沙箱，但可重新授权检索同一历史附件并导入新实例。
- 同一聊天的不同角色、不同聊天、并行执行和重试执行之间隔离；不得借用服务内“最近一个沙箱”。
- 完成、失败、取消、撤权及 TTL 过期均清理；进程崩溃后按启动扫描与既有沙箱标签/TTL 回收遗留资源。
- 文件不进入永久插件版本目录、素材库或 Web 静态目录，不将宿主临时目录挂入沙箱，不给沙箱 Docker Socket。
- 临时存储位置可由部署配置明确指定，默认在应用受限临时目录内；容量不足拒绝导入。临时附件不加入长期备份，恢复不能恢复旧任务的文件授权。
- 数据库只持久化附件关联及审计元数据，不存附件二进制、传输令牌或 MCP 会话令牌。
- 进程重启不承诺从中断命令续跑；沿用现有执行恢复规则，禁止自动重放结果未知的命令或重复发送回答。

## 9. 管理界面与审计

AI 节点编辑区域增加开关；仅一个兼容沙箱服务时自动绑定并展示名称，多个时才显示“附件处理沙箱”选择；额度使用统一配置弹窗，桌面和移动端一致。失败时保留表单输入，保存沿用 expectedVersion，重复点击不重复提交。

执行详情展示“附件导入”工具，关联插件服务、附件来源消息、文件名、类型、实际大小、哈希、沙箱代次、各阶段耗时及结果。区分未读取、导入成功、处理失败和任务已清理；导入成功不等于分析成功。

普通日志只记录允许的元数据和错误码，不记录正文、完整文件名、下载地址、命令正文、结果正文或凭据。文件名可能含敏感信息，UI 展示和保存遵循现有受保护详情、保留及删除规则；清理聊天后不得从附件审计泄露原内容。旧记录不回填。

至少区分：附件不属于本轮、权限撤销、类型不支持、文件已不可用、下载失败、体积超限、容量忙、沙箱能力不足、传输失败、哈希不符、超时、取消及会话失效。

## 12. 本地技术预研结论（2026-11-05）

已使用独立 Docker OpenSandbox、虚构文件和现有 MCP 适配代码验证流式二进制上传、创建后追加导入、同一会话读取、新任务隔离与清理。详见[预研脚本、环境和结果](experiments/attachment-sandbox/README.md)。这不是完整附件功能验收。

实施须落实三个已确认问题：SDK 原生上传会跟随符号链接，必须增加安全暂存与提交；文件写入 API 不直接接收 AbortSignal，HTTP 超时也不停止源生成器，必须联动取消下载和传输；既有文件命令失败可能使整个沙箱会话失效，需区分可恢复导入失败和不可继续的任务状态。不能只通过 Promise 超时或 Skill 指引解决这些问题。
