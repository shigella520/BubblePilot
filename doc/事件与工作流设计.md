# BubblePilot 事件与工作流设计

## 1. 设计原则

工作流是配置化的有向图，不是任意脚本。每个节点拥有明确的输入、输出、配置 Schema、错误策略和版本。编排器只负责图遍历和状态管理，具体业务行为由节点实现。

## 2. 工作流组成

```text
Trigger → Context → Node 1 → Condition → Node 2 / Node 3 → Reply → End
```

- **Trigger**：决定哪些消息进入工作流。
- **Context**：消息信封、变量、有限历史和运行元数据。
- **Node**：执行一个可复用动作。
- **Edge**：描述节点之间的下一跳和条件。
- **Execution**：保存一次运行的状态和轨迹。

## 3. 首期节点类型

| 类型 | 用途 | 副作用 |
| --- | --- | --- |
| `condition` | 判断字段、关键词或表达式 | 无 |
| `set-variable` | 设置或映射上下文变量 | 修改执行上下文 |
| `load-context` | 读取有限的消息历史或配置 | 只读 |
| `ai-chat` | 调用 OpenAI 兼容服务 | 外部网络调用 |
| `reply` | 向原聊天发送消息 | 外部写入 |
| `log` | 记录结构化诊断信息 | 写执行日志 |
| `end` | 明确结束当前分支 | 无 |

后续节点可扩展为 HTTP、定时、聚合、人工确认等，但必须先定义安全、超时、重试和权限边界。

## 4. 触发匹配

触发器条件按以下范围组合：

- 聊天或群聊范围；
- 发送者范围；
- 消息类型；
- 关键词、前缀或正则；
- 时间窗口；
- 是否允许由 Bot 自己发送的消息再次触发。

默认禁止 Bot 自己发送的回复再次触发同一工作流，除非显式启用并设置最大循环次数。

只有已启用的触发器和已发布的工作流版本可以处理生产消息。同一消息匹配多个触发器时，每个触发器按各自的幂等键创建独立逻辑执行；配置端应提示可能产生多次回复的冲突。触发条件预览不得执行回复、AI 调用等有副作用的节点。

## 5. 工作流定义示例

```yaml
schemaVersion: 1
name: summarize-and-reply
nodes:
  - id: check-command
    type: condition
    version: 1
    config:
      expression: "message.text startsWith '/sum'"
    onTrue: ask-ai
    onFalse: end
  - id: ask-ai
    type: ai-chat
    version: 1
    config:
      providerRouteId: default-ai-route
      promptTemplate: "Summarize the recent context in three bullets."
      timeoutMs: 30000
      maxOutputTokens: 500
    onSuccess: reply
    onFailure: end
  - id: reply
    type: reply
    version: 1
    config:
      textFrom: nodes.ask-ai.output.text
    onSuccess: end
  - id: end
    type: end
    version: 1
```

工作流定义发布前必须通过结构、节点类型、边引用、权限和资源限制校验。

## 6. 执行语义

- 工作流启动时锁定 `WorkflowVersion`。
- 节点默认串行执行；并行分支只有在节点和存储合同明确支持后启用。
- 每个节点有独立超时和最大重试次数。
- 可重试错误采用指数退避；不可重试错误直接进入失败状态。
- `reply` 节点以 `executionId + nodeId` 做发送幂等。
- AI 节点不得直接修改消息归档、权限或工作流配置。
- 工作流上下文设置大小和历史消息数量上限，避免无界增长。

### 6.1 AI Provider 路由语义

AI 节点引用版本化的 `providerRouteId`，而不是把服务地址或 Secret 写入工作流。节点启动时锁定路由快照，快照包含有序候选、配置版本、单请求超时和故障策略，但不复制 Secret 明文。

为避免 Retry 与 Fallback 含义混乱，统一使用以下术语：

- **Provider Attempt**：向一个 Provider 发起的一次实际调用。
- **Fallback**：同一节点重试轮次中，当前候选失败后切换到下一个候选。
- **Node Retry**：当前路由的可用候选全部耗尽后，节点按退避策略开始下一轮执行。
- **Degrade**：Provider 达到连续故障阈值后，在冷却期内降低有效优先级或退出常规候选。

路由规则：

1. 默认路由按 `AiProvider.sortOrder` 读取已启用候选；命名路由可以保存候选子集和显式顺序。每轮再叠加不改写配置的运行时健康状态。
2. 每个 Provider 每轮最多调用一次；成功得到有效输出后立即停止 Fallback。
3. 超时、连接失败、限流、可恢复的服务端错误、Provider 局部的鉴权或模型错误、空输出和结构无效可以按策略进入下一个候选；其中不可重试的 Provider 局部错误不应触发下一轮 Node Retry。
4. 请求取消、执行中断、工作流配置错误和明确的内容安全拒绝不得盲目切换候选。
5. 候选全部失败后，只有至少一个错误可重试且节点仍有预算时才进入 Node Retry；总调用次数受候选数、重试轮次、节点超时和执行预算共同限制。
6. 全部候选处于 `degraded` 时，每轮最多选择一个到达恢复时间的候选进行 `half-open` 探测，不并发放大故障。
7. 每次 Attempt 都记录 Provider、模型、候选序号、轮次、耗时、结果和脱敏错误码；最终输出仍必须通过 AI 输出安全检查。

默认降级只统计明确配置的 Provider 局部故障，例如连续超时、连接失败、限流或服务端错误。成功调用清除适用计数；达到阈值后进入有期限的 `degraded`，冷却探测成功再恢复。人工启停、人工排序和运行时降级是三类独立状态。

## 7. 失败与恢复

失败记录至少包含：`errorCode`、节点类型、节点版本、attempt、是否可重试、脱敏错误摘要和下一次重试时间。

达到重试上限后进入 `dead-lettered`，由管理页面提供人工重试或关闭操作。人工重试必须生成新的执行尝试，但保留原始执行链路。

## 8. 新增节点的要求

1. 定义节点名称、版本和配置 Schema。
2. 实现输入检查、执行逻辑、输出结构和错误分类。
3. 注册到节点注册表。
4. 增加成功、超时、重试、重复执行和敏感数据测试。
5. 更新本文件和工作流 Schema。
6. 通过 PR 发布，不能在生产环境直接替换已发布节点行为。
