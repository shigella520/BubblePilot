# BubblePilot 仓库目录规划

## 1. 规划目标

仓库采用单仓库、模块化单体结构。目录只在对应功能开始实现时创建，避免保留没有代码、测试或构建入口的空模块。

## 2. 目标目录

```text
BubblePilot/
├── app/                         # 应用启动、配置和模块组装
├── modules/
│   ├── ingestion/               # Webhook 接收、校验、标准化和幂等
│   ├── archive/                 # Chat、Message、搜索和保留策略
│   ├── automation/              # Trigger、Workflow、Execution 和节点注册表
│   ├── integrations/
│   │   └── bluebubbles/         # BlueBubbles REST/Webhook 适配器
│   ├── ai/                      # OpenAI 兼容 Provider 和 AI 节点
│   ├── auth/                    # 登录、二次验证、权限和审计
│   └── web/                     # 管理 API 和 Web 展示层
├── contracts/                   # OpenAPI、Webhook 和 Workflow Schema
├── migrations/                  # 数据库迁移，只追加不重写
├── deploy/                      # Docker Compose、反向代理和运维脚本
├── tests/                       # 仓库级合同测试和最小集成测试
├── doc/                         # 产品、架构、开发、部署和发布文档
├── .github/                     # CI、PR 模板和 Issue 模板
├── AGENTS.md
├── CONTRIBUTING.md
├── SECURITY.md
├── .env.example
└── README.md
```

实际使用的语言和框架确定后，可按生态惯例调整 `app/`、`modules/` 和测试目录名称，但不改变模块职责和依赖方向。

## 3. 依赖方向

```text
BlueBubbles Adapter ──> Ingestion ──> Archive
                                  └─> Automation ──> AI Provider / Reply Adapter
Web API ───────────────────────────────> Application Modules
Application Modules ───────────────────> Database
```

规则：

- 只有应用持久化层直接访问数据库。
- Web 层不直接调用 BlueBubbles 或 AI Provider。
- 工作流节点通过节点上下文和项目合同访问能力，不反向依赖 Web 控制器。
- BlueBubbles 供应商字段只能出现在适配器和契约映射层。
- 将来增加外部队列或独立 Worker 时，只替换执行传输层，不改变领域状态和幂等键。

## 4. 代码与配置边界

仓库允许保存：

- 迁移脚本、API/Workflow Schema 和匿名测试 Fixture；
- Docker Compose、环境变量示例和运维脚本；
- 节点实现、适配器实现和 Web 代码；
- 不含私密信息的品牌和文档素材。

仓库禁止保存：

- 真实聊天正文、附件、联系人信息和数据库导出；
- BlueBubbles 令牌、AI Key、密码或本地 `.env`；
- 生产执行日志、备份和死信内容；
- 通过配置执行任意服务器端代码的脚本。

## 5. 扩展目录的准入条件

新增目录必须同时具备至少一项实现、测试或构建入口，并在 PR 中说明：

- 所属模块和依赖方向；
- 对外合同和版本策略；
- 数据保存和敏感信息边界；
- 失败、重试和升级方式。
