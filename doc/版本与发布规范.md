# BubblePilot 版本与发布规范

## 1. 版本格式

正式版本采用 Semantic Versioning：`MAJOR.MINOR.PATCH`。

- `MAJOR`：不兼容的 API、工作流 Schema、数据行为或升级方式变更。
- `MINOR`：向后兼容的新功能或新节点类型。
- `PATCH`：向后兼容的问题修复和安全修复。

Git Tag 和 GitHub Release 使用 `vX.Y.Z`，例如 `v0.1.0`；应用和镜像内部版本使用 `0.1.0`。

## 2. 版本影响范围

下列内容发生不兼容变化时，必须在 Release Notes 中说明：

- Web API 和 Webhook Schema；
- 工作流定义和节点配置 Schema；
- BlueBubbles 适配器行为；
- 数据库迁移和数据保留策略；
- 认证、Secret 或 Compose 环境变量；
- 消息发送和幂等语义。

## 3. 镜像标签

镜像发布到 `ghcr.io/shigella520/bubblepilot`：

| 标签 | 用途 |
| --- | --- |
| `X.Y.Z` | 不可移动的精确版本 |
| `latest` | 最新正式版本，只在正式 Release 移动 |
| `sha-<commit>` | 精确定位构建提交 |
| `dev` | 可选开发构建，不用于生产 |

生产部署优先使用精确版本；使用 `latest` 必须明确接受自动升级风险。`dev` 会被下一次手动开发发布覆盖，验证部署需要可复现或回滚时应改用同次工作流产生的 `sha-<commit>`。

## 4. CI 与镜像发布

| 事件 | 完整验证 | 镜像构建 | 镜像推送 |
| --- | --- | --- | --- |
| 目标为 `main` 的 Pull Request | 是 | 是 | 否 |
| 推送到 `main` | 是 | 是 | 否 |
| 手动运行 `CI` | 是 | 是 | 否 |
| 手动运行 `Publish Dev Image` | 是 | 是 | `dev`、`sha-<commit>` |
| 推送 `main` 历史上的 `vX.Y.Z` Tag | 是 | 是 | `X.Y.Z`、`latest`、`sha-<commit>` |

主 CI 在发布正式镜像前验证 Tag 指向的提交属于 `main` 历史。普通 PR 和 `main` 提交只试构建镜像，不登录 GHCR，也不覆盖任何远端标签。

手动发布开发镜像时，在 GitHub Actions 中选择 `Publish Dev Image`，选择需要验证的功能分支后运行。工作流先执行与主 CI 相同的迁移、测试、构建和 Compose 校验，全部成功后才更新 `dev`；开发镜像发布使用串行并发组，避免两个运行同时争用可移动标签。

## 5. 正式发布流程

1. 从最新 `main` 创建 `codex/release-vX.Y.Z`。
2. 更新应用版本、Schema 版本和升级说明。
3. 检查数据库迁移、配置变更、权限变化和回滚方式。
4. 运行开发指南中全部验证命令。
5. 通过 Pull Request 合并到 `main`。
6. 确认目标提交已位于 `main`，在该提交创建并推送不可变 Tag `vX.Y.Z`。
7. 等待 CI 自动发布 `X.Y.Z`、`latest` 和 `sha-<commit>` 镜像。
8. 创建同名 GitHub Release 和变更说明。
9. 备份数据库后使用精确 `X.Y.Z` 镜像升级实例，确认健康检查和真实测试聊天闭环。

## 6. 发布说明最低内容

- 新功能、修复和已知限制；
- 工作流、API 或 BlueBubbles 兼容性；
- 数据库迁移和备份要求；
- 新增、修改和删除的环境变量；
- 安全修复及是否需要轮换 Secret；
- 升级、验证和回滚步骤。

发布失败时不重写 Tag，也不移动精确镜像标签；修复后发布新的 PATCH 版本。
