# 迭代需求：聊天级统一对话摘要

## 1. 迭代概述

### 1.1 背景

当前对话摘要压缩属于工作流中的 `load-context` 节点。摘要状态按聊天、工作流、节点和 profile 隔离，并且只有工作流执行到该节点时才检查压缩阈值。

这会造成同一个聊天在不同工作流之间存在多份摘要状态。当聊天消息快速增长、后续由另一个参与者触发工作流时，后一个工作流可能看不到尚未被前一个工作流压缩的消息。现有首次追赶逻辑还可能只处理一个压缩周期，导致更早的积压消息没有进入 AI 上下文。

### 1.2 目标

将摘要压缩从工作流节点级能力调整为聊天级后台能力：

- 每个聊天维护一份统一摘要状态；
- 所有聊天使用全局统一的摘要压缩配置；
- 每条消息归档后都检查是否达到压缩阈值；
- 达到阈值时独立创建摘要压缩任务和工作流执行任务；
- 工作流不等待摘要压缩，读取触发时可见的已提交摘要版本和消息范围；
- `load-context` 只负责读取上下文，不再负责维护摘要；
- 上下文提取动作只负责数据提取，不改变摘要状态。

### 1.3 非目标

- 本迭代不改变增量摘要、压缩批次、租约、乐观版本和原子提交的核心算法；
- 不删除或替换原始消息归档；
- 不引入外部消息队列或独立 Worker 服务；
- 不保证模型摘要在语义上零遗漏；需要精确事实时仍应支持原始消息检索；
- 不为不同工作流维护独立摘要。

## 2. 目标行为

### 2.1 聊天级摘要状态

摘要状态的归属从：

```text
instance + chat + workflow + node + profile
```

调整为：

```text
instance + chat + summary policy version
```

摘要状态至少包含：

- `summary`：压缩后的文本；
- `coveredThroughMessageIndex`：摘要已覆盖的聊天消息游标；
- `version`：乐观锁版本；
- `status`：`idle` 或 `compressing`；
- 最近一次压缩原因、Provider、模型、合同版本和时间。

原始 `Message` 始终是事实来源。摘要是可重建的派生索引，不能替代原文，也不能因消息进入摘要而立即删除原文。

### 2.2 全局统一摘要配置

系统只维护一套全局摘要配置，至少包括：

- 基础原始消息窗口 `messageLimit`；
- 压缩目标字符数 `characterLimit`；
- 单次压缩消息数 `compressionBatchSize`；
- 摘要 Provider Route；
- 摘要合同版本；
- 消息纳入规则和摘要时区规则。

配置变更必须产生新的 `summaryPolicyVersion`。新策略不能直接覆盖旧策略生成的状态；已有聊天需要按新策略逐步重建或明确继续使用旧策略，不能混用不同策略的摘要。

### 2.3 消息触发和双任务并行

消息完成归档后执行摘要阈值检查。未达到阈值时只创建正常工作流任务；达到阈值时同时创建：

1. 摘要压缩任务；
2. 当前消息对应的工作流任务。

两类任务不互相等待。摘要任务使用创建时固定的：

- `baseSummaryVersion`；
- `fromMessageIndex`；
- `throughMessageIndex`。

后续消息不能改变该任务的输入范围。

工作流任务使用触发消息的事件边界，不因排队时间变长而读入后续消息。

### 2.4 已提交版本读取规则

工作流只读取已提交的摘要版本。

例如第 11 条消息触发时，当前摘要为 version 3，version 4 正在生成：

```text
摘要任务：version 3 + 固定原始消息范围 → version 4
工作流任务：读取 version 3 + 截止第 11 条的未压缩原始消息
```

下一条消息到达时：

- 如果 version 4 已提交，读取 version 4 和其覆盖游标之后的消息；
- 如果 version 4 尚未提交，继续读取 version 3 和其覆盖游标之后的消息。

这相当于“摘要状态读已提交”，并叠加“按触发消息游标固定上下文”的事件快照语义。

### 2.5 `load-context` 职责

`load-context` 保留上下文读取能力，但删除摘要压缩职责。它只读取：

- 当前聊天最新的已提交摘要；
- 摘要覆盖游标之后、且不晚于触发消息的原始消息；
- 当前触发消息；
- 当前窗口涉及的参与者映射和消息派生数据。

节点不再拥有或修改摘要状态，也不再配置摘要 Provider、压缩批次或摘要开关。

### 2.6 上下文提取动作

上下文提取动作只执行字段提取、分类、结构化转换或校验，不触发摘要压缩，不推进摘要游标，不写入聊天摘要。

如需要区分职责，可将能力表达为：

- `load-chat-context`：读取聊天级摘要和历史；
- `extract-context`：从当前上下文提取结构化数据；
- `ai-chat`：消费上下文生成回复。

## 3. 并发、失败和恢复

- 同一聊天同一摘要策略同时最多一个有效压缩任务；使用数据库租约和乐观版本控制；
- 摘要调用失败、租约过期或版本冲突时，不推进 `coveredThroughMessageIndex`；
- 后续工作流继续使用上一次已提交摘要和增量原始消息；
- 应用重启后，未完成任务可依据租约恢复；
- 摘要任务和工作流任务均以消息索引作为幂等边界；
- 工作流不得把排队期间新入库的消息带入既有执行；
- 如果旧摘要加未压缩消息超过安全上下文上限，不得静默丢弃，应记录上下文不完整状态并按既定重试或失败策略处理。

## 4. 数据库和接口影响

### 4.1 数据库

- 新增或改造聊天级摘要状态表；
- 压缩操作表改为关联聊天级摘要状态，不再要求工作流节点归属；
- 保留 `base_version`、消息范围、租约、耗时、Token 和错误码；
- 消息保留、脱敏和删除操作必须同步清空对应聊天摘要并递增版本；
- 旧的工作流级摘要状态标记为 legacy，不直接合并为新摘要。

### 4.2 工作流合同

- 删除 `load-context` 中的摘要开关、摘要 Route 和压缩批次配置；
- 保留消息窗口和读取视图所需配置；
- 已发布工作流应通过兼容默认值读取聊天级摘要；
- 工作流执行诊断记录实际使用的摘要版本、覆盖游标和未压缩消息数量。

### 4.3 AI 诊断

摘要压缩 Attempt 继续使用 `purpose = context-summary`，但不再强制绑定某个工作流执行或节点。诊断必须能从聊天、摘要版本、压缩操作和 Provider Attempt 关联完整链路。

## 5. 执行与审计中的可观测性

摘要压缩不属于工作流执行，因此不能继续作为工作流执行列表中的执行状态、节点结果或缓存状态展示。执行与审计模块仍应提供摘要压缩轨迹，但需要将其作为独立的后台操作类型。

### 5.1 工作流执行区域

工作流执行列表和详情移除：

- 摘要压缩成功/失败/处理中图标；
- 将摘要压缩状态并入工作流状态的汇总字段；
- 以工作流执行 ID 作为摘要压缩的归属标识。

工作流执行详情保留只读的上下文引用，用于解释该次执行使用了什么上下文：

- `chatId`；
- `triggerMessageIndex`；
- `summaryVersion`；
- `summaryCoveredThroughIndex`；
- `uncompressedMessageCount`；
- 是否使用旧摘要版本或发生上下文降级。

这些字段表示“本次执行读取了什么”，不表示“本次执行创建或拥有了什么摘要任务”。详情可以提供跳转到对应聊天摘要轨迹的链接。

### 5.2 独立的对话压缩轨迹区域

在“执行与审计”页面新增独立的“对话压缩”区域或标签页，与“工作流执行”和“审计事件”并列。列表每一行代表一次摘要压缩操作，而不是一次工作流执行。

建议展示字段：

- 时间；
- 聊天名称和 Provider Chat ID；
- 操作状态：`queued`、`running`、`succeeded`、`failed`、`superseded`；
- 压缩原因：消息阈值、字符安全阈值、初始追赶或策略重建；
- 输入摘要版本和输出摘要版本；
- `fromMessageIndex`、`throughMessageIndex`；
- Provider、模型和耗时；
- Prompt/Completion Token（仅显示计量值）；
- 错误码；
- 关联的 `correlationId` 和 `providerAttemptId`。

详情页可以查看操作参数、状态变化、游标和失败诊断，但不得展示完整聊天正文、完整 Prompt、原始 Provider 响应、Secret 或图片 Base64。摘要正文是否可查看沿用敏感数据二次验证和消息查看权限，不默认放入列表。

### 5.3 筛选、关联和审计边界

- 对话压缩轨迹支持按聊天、时间、状态、压缩原因和 Provider 筛选；
- 从工作流执行详情可以跳转到“该执行读取的摘要版本”；
- 从压缩操作详情可以反向查看在该摘要版本之后执行的工作流，但只显示关联 ID 和时间，不把工作流归属写回压缩任务；
- 压缩任务是系统后台操作，`actorType` 应标记为 `system`；
- 产生、成功、失败、重试和人工重建等摘要状态变化写入可审计的操作轨迹；
- 普通工作流运行不因摘要压缩失败而标记为工作流失败，除非上下文读取本身按照明确策略进入 `context-incomplete`。

## 6. 迁移和发布要求

1. 新增追加式数据库迁移，不修改已发布迁移；
2. 从原始消息重建聊天级摘要，不能直接拼接已有工作流级摘要；
3. 重建期间允许继续使用旧摘要加原始增量消息；
4. 重建完成后旧状态只用于兼容读取和排障；
5. 更新工作流 Schema、节点注册表、管理端配置和执行详情；
6. 同步更新技术设计、事件与工作流设计、部署与运维文档；
7. 发布说明必须包含备份、迁移耗时、失败恢复和回滚限制。

## 7. 验收标准

- 同一聊天的多个工作流读取同一摘要版本和覆盖游标；
- 每条归档消息都会触发一次阈值检查，但未达阈值不调用摘要模型；
- 达到阈值的消息同时创建摘要任务和工作流任务，工作流无需等待摘要完成；
- 摘要任务输入范围固定，不会吸收任务创建后的新消息；
- 工作流执行只读取触发消息边界前的内容；
- 摘要未完成时，后续工作流继续使用上一版已提交摘要；
- 摘要成功后，后续工作流自动读取新版本；
- 摘要失败、重启、租约过期和并发冲突均不会推进错误游标；
- 第三个参与者加入后，之前已归档的聊天内容不会因为未经过某个工作流而丢失；
- 消息删除或保留策略执行后，摘要同步清理；
- `load-context` 和上下文提取动作不会隐式触发摘要压缩；
- 工作流执行列表不再把摘要压缩显示为工作流执行状态；
- 执行详情能显示本次读取的摘要版本和消息水位线；
- “执行与审计”提供独立的对话压缩轨迹列表、详情、筛选和关联跳转；
- 对话压缩轨迹不保存或展示完整聊天正文、完整 Prompt、Secret 或原始响应；
- `pnpm verify`、`pnpm security:check` 和 PostgreSQL 集成测试通过。

## 8. 待确认产品决策

- 全局摘要配置是否允许管理员按聊天启用/停用，还是所有已监听聊天强制启用；
- 摘要是否默认包含机器人自己发送的消息；
- 摘要压缩失败持续多久后，将工作流标记为 `context-incomplete`；
- 全局配置变更后，历史聊天是后台重建，还是只在下次消息到达时懒重建；
- 是否在本迭代提供原始消息检索节点，以补足摘要的语义遗漏。
