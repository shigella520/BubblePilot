# BubblePilot 数据模型与生命周期

## 1. 数据归属

应用数据库保存 BubblePilot 自己的配置、归档和执行事实。BlueBubbles 负责消息发送和外部事件产生，但不负责 BubblePilot 的工作流版本、节点轨迹或审计记录。

仓库只保存迁移脚本、协议、匿名测试 Fixture 和部署配置，不保存生产聊天数据。

## 2. 核心实体

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| `Chat` | 一对一聊天或群聊 | `id`, `providerChatId`, `type`, `displayName`, `enabled` |
| `Message` | 归档后的标准消息；内容到期后保留必要元数据 | `id`, `providerMessageId`, `chatId`, `senderId`, `sentAt`, `body`, `contentHash`, `contentRedactedAt` |
| `InboundEvent` | 原始 Webhook 的幂等记录和自动化判定 | `eventId`, `provider`, `receivedAt`, `status`, `automationOutcome`, `payloadHash` |
| `BotTrigger` | 消息匹配规则 | `id`, `chatScope`, `conditions`, `workflowId`, `enabled` |
| `Workflow` | 工作流逻辑容器 | `id`, `name`, `status`, `publishedVersion` |
| `WorkflowVersion` | 不可变的发布版本 | `workflowId`, `version`, `definition`, `publishedAt` |
| `WorkflowExecution` | 一次工作流运行 | `executionId`, `eventId`, `workflowVersion`, `status`, `startedAt` |
| `NodeExecution` | 一个节点的执行轨迹 | `executionId`, `nodeId`, `status`, `attempt`, `durationMs`, `errorCode` |
| `AiProvider` | OpenAI 兼容服务配置 | `id`, `name`, `apiKind`, `baseUrl`, `model`, `secretRef`, `enabled`, `sortOrder`, `requestTimeoutMs`, `version` |
| `AiProviderRoute` | AI 节点使用的有序候选和恢复策略 | `id`, `name`, `providerIds`, `retryPolicy`, `fallbackEnabled`, `degradePolicy`, `version`, `enabled` |
| `AiProviderHealth` | 不覆盖人工顺序的运行时健康快照 | `providerId`, `state`, `consecutiveFailures`, `degradedUntil`, `lastSuccessAt`, `lastFailureAt` |
| `AiProviderAttempt` | 一次实际 Provider 调用 | `executionId`, `nodeId`, `routeVersion`, `providerId`, `providerName`, `providerVersion`, `model`, `round`, `sequence`, `selectionHealthState`, `healthState`, `status`, `durationMs`, `errorCode` |
| `AdminSession` | Web 管理会话；只保存随机 Token 的哈希 | `id`, `tokenHash`, `expiresAt`, `lastSeenAt`, `revokedAt` |
| `SensitiveOperationGrant` | 绑定管理会话的短时效二次验证授权 | `sessionId`, `verifiedAt`, `expiresAt` |
| `AuditEvent` | 登录、二次验证、敏感操作和配置变更 | `actorType`, `actorSessionId`, `action`, `targetType`, `targetId`, `outcome`, `correlationId`, `metadata`, `occurredAt` |
| `DataExportJob` | 受控导出的范围、冻结计数、所有者和短时状态 | `actorType`, `actorSessionId`, `chatId`, `sentFrom`, `sentTo`, `snapshotAt`, `messageCount`, `executionCount`, `status`, `expiresAt` |

M1 已创建 `InboundEvent`、`Chat` 和 `Message` 表，对应迁移为 `migrations/0001_message_ingestion.sql`。M2 通过 `migrations/0002_workflow_foundation.sql` 创建 `Workflow`、`WorkflowVersion`、`BotTrigger`、`WorkflowExecution`、`NodeExecution` 和出站发送记录。M3 通过 `migrations/0003_ai_provider_routing.sql` 创建 Provider、健康事件、不可变路由版本和 Provider Attempt。M4 的 `migrations/0004_web_admin.sql` 创建管理会话、二次验证授权和审计事件；`migrations/0005_data_exports.sql` 创建受所有者隔离的导出任务。`migrations/0006_execution_recovery.sql` 补充人工恢复和关闭字段；`migrations/0007_inbound_automation_outcomes.sql` 为入站事件补充稳定自动化判定，并把无法反推的历史事件标为 `not-evaluated`；`migrations/0008_ai_attempt_error_category.sql` 为 Provider Attempt 补充稳定错误类别；`migrations/0009_message_content_retention.sql` 为消息增加内容清理时间和待清理索引。会话撤销或过期后不能再获得敏感授权，删除会话时级联删除授权；审计事实和已创建导出任务保留，但失去原会话身份的任务不能继续下载。

默认 Provider 路由继承 `AiProvider.sortOrder`；命名路由可以选择候选子集并保存显式顺序。两类固定顺序都属于配置事实，运行时健康状态只能计算当前有效顺序，不能回写它们。

## 3. 状态生命周期

### 3.1 入站事件

```text
accepted → completed
         ├→ ignored
         └→ failed → accepted（同一事件再次投递）
```

`retrying` 和 `dead-lettered` 属于工作流执行状态，不改写入站事件已经归档或忽略的事实。

入站接入状态与自动化判定是两个正交维度。`automationOutcome` 使用以下稳定机器码：

| 值 | 含义 |
| --- | --- |
| `unsupported-event` | Webhook 合法，但不是当前支持的消息事件 |
| `chat-not-monitored` | 聊天未启用监听，正文未归档且未进入匹配 |
| `evaluation-pending` | 消息已归档，但工作流判定尚未完成；重复投递可以安全恢复 |
| `not-evaluated` | 历史事件无法反推结果，或当前实例没有配置工作流能力 |
| `no-active-triggers` | 消息已归档，但当时没有活动触发器 |
| `no-trigger-match` | 存在活动触发器，但条件均未命中 |
| `matched` | 至少一个触发器命中并进入幂等执行创建 |

新消息归档后先写入 `evaluation-pending`，工作流成功完成匹配和幂等执行创建后再原子更新为最终判定。若队列已满、等待超时或调度过程在最终判定前中断，事件保持 `evaluation-pending`；同一 `provider + eventId` 重复投递时允许再次进入匹配。执行唯一键和回复幂等键保证已经创建或发送的部分不会重复产生副作用。

除 `evaluation-pending` 外，同一事件重复投递不再次匹配或执行，只返回首次处理持久化的 `automationOutcome`。历史 `not-evaluated` 不会因后续重投而意外使用当前配置补跑；运行时健康变化、后续配置变更和人工恢复也不回写最终历史判定。

### 3.2 工作流版本

```text
draft → validated → published → superseded
  └──────────────→ invalid
```

已发布版本不可原地修改。修改配置必须创建新版本，正在执行的实例继续使用启动时锁定的版本。

工作流容器可在 `active` 与 `inactive` 之间整体切换；`inactive` 只阻止触发器为新消息创建执行，不取消已开始执行、不修改不可变版本或触发器配置，也不在恢复后追溯消息。

### 3.3 执行记录

```text
created → running → succeeded
running → skipped
running → retrying → running
running → failed
running → dead-lettered
failed / dead-lettered → created（新建关联恢复执行）
逾期 retrying → failed + created（原执行终止并新建关联恢复执行）
retrying / failed / dead-lettered → closed（人工关闭）
```

计划重试恢复使用执行状态、当前节点和 `nextRetryAt` 的条件更新，避免人工关闭或人工接管后旧执行器重新运行。人工重试追加新的执行尝试并保留原有节点轨迹；人工关闭只结束后续恢复，不删除失败事实。两种操作都必须审计。

### 3.4 AI Provider 健康状态

```text
healthy → degraded → half-open → healthy
                    └────────→ degraded
```

- `healthy`：按管理员配置顺序正常参与候选选择。
- `degraded`：达到配置的连续故障阈值，在冷却期内降低有效优先级或暂不参与常规选择。
- `half-open`：冷却结束后只允许受控探测；成功恢复为 `healthy`，失败重新进入 `degraded`。
- 管理员停用是配置状态，不等同于运行时降级；停用的 Provider 不参与新路由快照。
- 健康快照需要持久化，防止进程重启让仍在冷却的 Provider 提前恢复。成功调用清除适用的连续故障计数；自动降级、恢复和人工重置必须保留健康事件或审计事实，不修改 `sortOrder`。

### 3.5 受控导出任务

```text
awaiting-confirmation → ready → expired
          ├──────────→ revoked
          └──────────→ expired
```

- `snapshotAt` 冻结可见数据边界，预览后才写入且 `createdAt > snapshotAt` 的消息或执行不会进入下载。
- `awaiting-confirmation` 默认 5 分钟过期；只有记录数和冻结时间与预览完全一致时才能确认。
- `ready` 从确认时起提供 10 分钟下载窗口；`downloadedAt` 只记录首次成功读取，不延长有效期。
- `expired` 是根据 `expiresAt` 计算的外部状态，不回写历史行；`revoked` 是显式终止事实。
- 任务只保存范围、计数和状态，不保存临时正文文件。下载内容每次按冻结边界动态生成，并再次检查聊天当前仍启用监听。

## 5. 幂等键

- 入站事件：`provider + eventId`。
- 消息归档：`provider + providerMessageId`。
- 工作流执行：`eventId + workflowVersionId + triggerId`。
- 回复发送：`executionId + replyNodeId`。

幂等记录必须有唯一约束，并保存最终状态或可恢复状态，不能只依赖内存 Map。

BlueBubbles `new-message` 没有独立事件 ID，当前适配器使用 `new-message:<message-guid>` 作为 `eventId`。数据库唯一约束分别位于 `inbound_events(provider, external_event_id)` 和 `messages(provider, provider_message_id)`。

首次工作流执行唯一约束位于 `workflow_executions(provider, external_event_id, trigger_id, workflow_version_id)`；人工恢复使用带恢复执行 UUID 的内部事件键，同时以唯一的 `retry_of_execution_id` 保证同一源执行不会因重复点击创建两个直接子执行。`recovery_attempt` 从原执行的 0 开始逐次递增，历史行不被新尝试覆盖。

回复幂等键位于 `outbound_deliveries.idempotency_key`。已确认发送不会再次调用供应商；`sending` 或 `unknown` 状态在人工确认前也禁止自动或人工重发。人工关闭只更新执行状态，不删除原错误、节点轨迹、AI Provider Attempt 或出站记录。

## 6. 保存与删除

- 默认只对启用监听的聊天保存消息正文。
- `MONITORED_CHAT_IDS` 只为尚未发现的聊天提供初始监听状态；聊天进入数据库后以 `Chat.enabled` 为权威状态，管理端更新使用 `version` 防止并发覆盖。空配置默认不归档任何正文。
- 启用监听默认只影响此后到达的新消息，不自动回填历史；停用监听不删除既有归档。
- 附件只保存必要元数据，是否保存文件内容由独立配置控制。
- 受控导出只允许单个已监听聊天、最长 31 天、最多 10,000 条和预估 25 MB；默认不包含 Secret、完整 Prompt、原始 Payload、节点输入输出或错误详情。
- 消息删除、导出预览/确认/下载/撤销、凭据变更和工作流停用必须产生审计记录。
- `MESSAGE_RETENTION_DAYS` 默认 90 天，按消息进入 BubblePilot 的 `createdAt` 计算，不使用可能来自历史同步的供应商 `sentAt`。设为 `0` 表示管理员显式接受无限期保留风险并关闭自动清理。
- 清理任务启动后立即运行，之后每小时尝试一个最多 10,000 条的有界批次。到期时只把正文置空、附件元数据替换为空数组，并记录 `contentRedactedAt`；聊天、消息 ID、发送者、时间、内容哈希、入站事件和执行引用继续保留，用于幂等、追踪和审计。
- `evaluation-pending` 消息、仍处于 `created`、`running`、`retrying` 的执行源消息、尚未创建恢复子执行的 `failed`/`dead-lettered` 叶子执行，以及尚未过期的导出快照范围不会被清理。执行关闭、恢复链产生后继或导出到期后由后续批次重新评估；恢复链中最新的可恢复叶子仍会继续保护源内容。
- 内容清理与 `message.content.retention` 系统审计写入同一 PostgreSQL 事务；保留任务和导出预览、确认、下载使用同一 advisory lock，避免冻结导出范围在有效期内被清理改写。清理任务使用非阻塞锁获取，导出事务占用锁时本轮直接延期到下一次调度，关停过程不会无限等待锁。
