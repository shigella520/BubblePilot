# BubblePilot 数据模型与生命周期

## 1. 数据归属

应用数据库保存 BubblePilot 自己的配置、归档和执行事实。BlueBubbles 负责消息发送和外部事件产生，但不负责 BubblePilot 的工作流版本、节点轨迹或审计记录。

仓库只保存迁移脚本、协议、匿名测试 Fixture 和部署配置，不保存生产聊天数据。

## 2. 核心实体

| 实体 | 说明 | 关键字段 |
| --- | --- | --- |
| `Chat` | 一对一聊天或群聊 | `id`, `providerChatId`, `type`, `displayName`, `enabled` |
| `Message` | 归档后的标准消息 | `id`, `providerMessageId`, `chatId`, `senderId`, `sentAt`, `body`, `contentHash` |
| `InboundEvent` | 原始 Webhook 的幂等记录 | `eventId`, `provider`, `receivedAt`, `status`, `payloadHash` |
| `BotTrigger` | 消息匹配规则 | `id`, `chatScope`, `conditions`, `workflowId`, `enabled` |
| `Workflow` | 工作流逻辑容器 | `id`, `name`, `status`, `publishedVersion` |
| `WorkflowVersion` | 不可变的发布版本 | `workflowId`, `version`, `definition`, `publishedAt` |
| `WorkflowExecution` | 一次工作流运行 | `executionId`, `eventId`, `workflowVersion`, `status`, `startedAt` |
| `NodeExecution` | 一个节点的执行轨迹 | `executionId`, `nodeId`, `status`, `attempt`, `durationMs`, `errorCode` |
| `AiProvider` | OpenAI 兼容服务配置 | `id`, `name`, `apiKind`, `baseUrl`, `model`, `secretRef`, `enabled`, `sortOrder`, `requestTimeoutMs`, `version` |
| `AiProviderRoute` | AI 节点使用的有序候选和恢复策略 | `id`, `name`, `providerIds`, `retryPolicy`, `fallbackPolicy`, `degradePolicy`, `version`, `enabled` |
| `AiProviderHealth` | 不覆盖人工顺序的运行时健康快照 | `providerId`, `state`, `consecutiveFailures`, `degradedUntil`, `lastSuccessAt`, `lastFailureAt` |
| `AiProviderAttempt` | 一次实际 Provider 调用 | `executionId`, `nodeId`, `routeVersion`, `providerId`, `providerVersion`, `model`, `round`, `sequence`, `status`, `durationMs`, `errorCode` |
| `AuditRecord` | 敏感操作和配置变更 | `actorId`, `action`, `target`, `createdAt`, `result` |

M1 已创建 `InboundEvent`、`Chat` 和 `Message` 表，对应迁移为 `migrations/0001_message_ingestion.sql`。其余实体按路线图在有实现入口时追加。

默认 Provider 路由继承 `AiProvider.sortOrder`；命名路由可以选择候选子集并保存显式顺序。两类固定顺序都属于配置事实，运行时健康状态只能计算当前有效顺序，不能回写它们。

## 3. 状态生命周期

### 3.1 入站事件

M1 当前状态：

```text
accepted → completed
         ├→ ignored
         └→ failed → accepted（同一事件再次投递）
```

M2 引入执行队列后扩展 `retrying` 和 `dead-lettered`，但不改变已有状态含义。

### 3.2 工作流版本

```text
draft → validated → published → superseded
  └──────────────→ invalid
```

已发布版本不可原地修改。修改配置必须创建新版本，正在执行的实例继续使用启动时锁定的版本。

### 3.3 执行记录

```text
created → running → succeeded
running → skipped
running → retrying → running
running → failed
running → dead-lettered
dead-lettered → retrying → running（人工重试）
dead-lettered → closed（人工关闭）
```

人工重试追加新的执行尝试并保留原有节点轨迹；人工关闭只结束后续恢复，不删除失败事实。两种操作都必须审计。

### 3.4 AI Provider 健康状态

```text
healthy → degraded → half-open → healthy
                    └────────→ degraded
```

- `healthy`：按管理员配置顺序正常参与候选选择。
- `degraded`：达到配置的连续故障阈值，在冷却期内降低有效优先级或暂不参与常规选择。
- `half-open`：冷却结束后只允许受控探测；成功恢复为 `healthy`，失败重新进入 `degraded`。
- 管理员停用是配置状态，不等同于运行时降级；停用的 Provider 不参与新路由快照。
- 健康快照需要持久化，防止进程重启让仍在冷却的 Provider 提前恢复。成功调用清除适用的连续故障计数；自动降级、恢复和人工重置必须保留健康事件或审计事实，不修改 `sortOrder`。

```json
  "eventId": "new-message:fictional-message-id",

  }

```

## 5. 幂等键

- 入站事件：`provider + eventId`。
- 消息归档：`provider + providerMessageId`。
- 工作流执行：`eventId + workflowVersionId + triggerId`。
- 回复发送：`executionId + replyNodeId`。

幂等记录必须有唯一约束，并保存最终状态或可恢复状态，不能只依赖内存 Map。

BlueBubbles `new-message` 没有独立事件 ID，当前适配器使用 `new-message:<message-guid>` 作为 `eventId`。数据库唯一约束分别位于 `inbound_events(provider, external_event_id)` 和 `messages(provider, provider_message_id)`。

## 6. 保存与删除

- 默认只对启用监听的聊天保存消息正文。
- M1 通过启动配置 `MONITORED_CHAT_IDS` 计算 `Chat.enabled`；空配置默认不归档任何正文。
- 启用监听默认只影响此后到达的新消息，不自动回填历史；停用监听不删除既有归档。
- 附件只保存必要元数据，是否保存文件内容由独立配置控制。
- 消息删除、批量导出、凭据变更和工作流停用必须产生审计记录。
- 清理任务必须按保留策略执行，并且不能删除仍被执行记录引用的必要元数据。
