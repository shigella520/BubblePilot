### P1 查询改写

### P2 向量存储重构（需要全量重建）

现状：`embedding` 列是不带维度的 `vector`，3072 维。pgvector 的索引最多支持 2000 维（`halfvec` 最多 4000 维），且列不定维度就无法建索引，所以每次检索都是对整个聊天精确扫描。

方案：

1. **降维**：请求向量服务输出 1024 维（或 768 维）。Gemini 的 embedding 模型支持截断输出维度（Matryoshka），检索质量损失通常很小。上线前用 `dimensions` 参数实测中转站是否支持，并用检索测试对比召回。
2. **半精度存储**：列改为 `halfvec(1024)`，单个向量从约 12 KB 降到约 2 KB。
3. **索引与冗余字段**：`memory_embeddings` 增加 `chat_id`、`generation_id`。数据量在每群几万分块的规模时，按聊天精确扫描已足够快（预计 30～80 毫秒）；再建 HNSW（`halfvec_cosine_ops`，开启 `hnsw.iterative_scan` 配合聊天过滤）作为后续增长的保障。
4. **重建方式**：配合长期检索整改 R3 的自动切换，新建代次、后台补全、覆盖后自动切换，旧代次 3 天后清理。按今天的速度，约 4.8 万条消息需要 1～2 小时，向量调用费用很低。

预期：向量检索 0.95 秒降到 0.1 秒以内，向量表从 265 MB 降到约 40 MB。

## 3. 实施顺序

1. **P0 全部 + P3 清理任务**：一次发布，带一个只加索引的迁移（`CREATE INDEX CONCURRENTLY` 不锁表）；数据库参数随 compose 调整，需重启 postgres（约 10 秒）。
2. **P1**：按 P1-1、P1-2、P1-3 优先，其余随长期检索整改一起做。
3. **P2**：与长期检索整改第 3 期（自动切换代次）合并，借自动切换完成全量重建。
4. 每步上线前后用同一组 `EXPLAIN ANALYZE`（向量检索、覆盖率、关键词查询、上下文加载、聊天列表）记录耗时对比。

## 4. 实施记录

- **第 1 步（本地已完成，未部署）**：P0-1 数据库参数（compose）；P0-2 统计刷新与小表自动分析阈值；P0-3 去掉每秒的失效向量清理，改由数据整理任务删除失效分块；P0-4/P0-5 记忆任务与归属任务的可领取部分索引；P0-6 按消息查找执行改为两条索引路径（线上实测 1.35 秒 → 0.06 秒）；P0-7 聊天消息数改用序号计数（线上 11 个聊天核对一致）。P3 中记忆与诊断数据的整理随第 1 步完成；执行记录 90 天可配置保留放到后续单独实现（涉及多张关联表与设置界面）。

- **第 2 步 P1（迁移 0084）**：P1-1 执行历史边界在 TypeScript 中读取一次、SQL 内联范围条件（未识别的边界形态回退到原函数）；P1-2 启用 `pg_trgm`，管理台消息搜索与模型关键词查询改为 `LIKE` 走三元组索引；P1-3 向量检索两段式（先取最近邻，再做来源检查）；P1-5 原始上下文首次窗口不再从 0 计数；P1-6 运行状态按状态分别计数走索引；P1-7 AI 用量一次扫描；P1-9 随长期检索 R7。改写前后 SQL 由等价性集成测试比对。未做：P1-4 改为由健康接口缓存解决；P1-8 未改；执行列表的 JSON 列属于公开接口未裁剪。
- **第 3 步 P2/P3（迁移 0083）**：向量表增加 `embedding_half`、`chat_id`、`generation_id`；精度可选（float32 ≤ 2000 维、float16 ≤ 4000 维），请求按配置维度输出；创建代次时建立类型化表达式的 HNSW 部分索引，检索使用相同表达式并开启 `hnsw.iterative_scan`。重建方式改为：保存新模型立即切换、从零补全，旧代次可立即清理或保留期满自动清理。执行明细（节点、工具、路由、图片输入）按可配置天数（默认 90）清理，执行记录、发送、归属与用量保留；`inbound_events` 被消息引用，不清理。实测：1024 维、单聊天 6000 分块精确扫描约 30 毫秒（线上 3072 维为 0.95 秒）。
- **上线后实测（2026-11-27，切换到 qwen3.7-text-embedding-flash 1024 维 float32 并清理旧代次后）**：8 个已启用聊天 48,801 条消息全部索引完成，无失败任务；最大聊天（10,716 个分块）向量检索走 HNSW 索引，0.95 秒降到 17～46 毫秒；数据库 1.06 GB 降到 990 MB，向量表 265 MB 降到 157 MB（删除后的空间由 PostgreSQL 复用，文件不缩小，无需 `VACUUM FULL`）。
