# BubblePilot 可靠性演练记录

## 1. 目的与记录规则

本文给出 M5 的可复现演练步骤，并记录实际执行证据。任何环境的演练都必须记录日期、镜像精确标签或 Commit、迁移版本、操作者、耗时、结果和后续问题；不得粘贴 Secret、真实消息正文、完整 Prompt 或数据库转储内容。

状态只使用：`通过`、`失败`、`待执行`。脚本语法检查或单元测试不能替代真实 PostgreSQL 恢复与镜像回滚，因此必须分开记录。

## 2. 死信恢复演练

### 自动化步骤

```bash
pnpm vitest run tests/workflow-application.test.ts tests/reliability-guards.test.ts
```

覆盖点：

- 可重试故障耗尽预算后进入 `dead-lettered`；
- 人工重试创建带 `retryOfExecutionId` 的新执行并保留原执行；
- 重复点击不会创建第二个直接恢复子执行；
- 正常等待中的 `retrying` 拒绝人工接管，逾期后才允许创建恢复执行；
- 等待期间人工关闭或逾期接管后，旧执行器不会继续下一次节点或 Provider 调用；
- `unknown` 出站状态拒绝人工重试，但允许人工关闭；
- 限流、并发上限和有限等待队列产生稳定错误。

### 目标环境步骤

1. 使用虚构测试聊天触发一个明确失败且没有未知出站结果的工作流。
2. 在 Web“执行与审计”进入恢复队列，记录原执行 ID、状态和错误码。
3. 在正常等待期尝试人工重试，确认返回 `EXECUTION_RETRY_STILL_ACTIVE`；等待超过卡住阈值后再重试，确认新执行链接到原执行，且只产生预期的一次回复。
4. 再制造一次回复结果未知场景，确认人工重试被拒绝，核对 BlueBubbles 后人工关闭。
5. 检查 `execution.retry`、`execution.close` 审计事件均只有 ID、结果和关联 ID。

## 3. 备份恢复演练

```bash
BACKUP_PATH=$(scripts/backup-postgres.sh)
scripts/verify-postgres-backup.sh "$BACKUP_PATH"
```

通过标准：

- 备份文件非空且生成 SHA-256 文件；
- custom-format 备份能恢复到脚本随机创建的临时数据库；
- `schema_migrations` 可查询，消息、执行、Provider、会话和导出关键表均存在；
- 临时恢复数据库在成功或失败后都被删除；
- 生产数据库名称、大小和连接状态未改变。

## 4. 升级与回滚演练

1. 把当前正式镜像和目标镜像都固定到精确 `X.Y.Z` 或 `sha-<commit>`，不得使用 `dev` 或 `latest` 作为回滚锚点。
2. 创建备份并运行：

```bash
scripts/preflight-upgrade.sh "$BACKUP_PATH"
```

3. 拉取并启动目标镜像，确认迁移只前向执行：

```bash
docker compose pull app
docker compose up -d --no-build
scripts/diagnose.sh
```

4. 验证登录、监听、虚构测试消息、工作流、AI Fallback、执行查询和导出预览。
5. 若应用需要回滚，把 `BUBBLEPILOT_IMAGE` 改回上一精确镜像并重新创建应用容器。数据库不做反向迁移；若旧应用不兼容新 Schema，改为从演练备份恢复整个数据库和应用版本。
