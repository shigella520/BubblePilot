# 迭代需求：独立生图插件与图片编辑

状态：待实施规划（2026-11-27）。接入独立的生图 MCP 插件，首个上游为 OpenAI Images 兼容中转站上的 gpt-image-2，支持文生图，以及对用户发来的图片做编辑。本文梳理 BubblePilot 改造、新插件实现与受牵连插件的同步调整。第 8 节的决策已确认（D1 采用多目标），上游接口已探测验证（第 4.5 节）。

## 改造点速览

1. **BP 合同去沙箱化**：图片回复和附件导入的合格目标，从“必须拥有 `prepare_sandbox`、`run_command` 等固定工具名”改为“声明对应协议能力并指定锚定工具”。OpenSandbox 不声明锚定工具时按原规则处理，行为不变。
2. **新增独立插件** `bubblepilot-image-gen`：持有上游 Key，提供生成、编辑和可选预览工具；复用 `io.bubblepilot/image-export`、`io.bubblepilot/attachments` v1 二进制通道和单次票据语义。
3. **图片编辑闭环**：用户图片经现有 `import_chat_attachment` 导入插件的会话工作区，再由 `edit_image` 引用；产物经现有 `prepare_chat_attachment` 导出，由 Reply 节点发送。
4. **节点多目标**（D1 已定为方案 B）：同一节点可同时绑定沙箱与生成器，兰博保留 SVG 绘图和文件处理，同时获得生图和改图能力。
5. **受牵连范围**：OpenSandbox 不需要修改协议，但须做回归；Firecrawl 不受影响；生产工作流只在管理员显式改绑后变化。

## 1. 目标与边界

**目标**

- 群内成员请求“画一张……”时，模型调用生图工具，产出 PNG 或 JPEG，并作为回复附件发送。
- 成员发图并要求“把这张改成……”时，模型导入该图片，调用编辑工具，发送编辑结果；也支持引用历史消息中的图片。
- 上游 Key、费用和次数限制只存在于插件服务内，模型、沙箱和 BP 数据库都不保存 Key。

**非目标**

- 不在 BP 内置生图 Provider，不修改 AI 路由。生图不经过聊天模型的多模态输出通道。
- 不支持视频、动图生成，不支持在一次回复里发送多张图。沿用“每轮一个附件”的现行合同。
- 不自动修改生产工作流，不扩大历史读取、联网或聊天授权范围。
- 不承诺上游内容审核的结果；被拒绝的请求如实告知，不尝试绕过。

## 2. 用户闭环

```text
成员：“兰博，把这张照片改成水彩风格”（附图或引用图片）
  └─ 模型：import_chat_attachment(attachment_ref) → 得到 /workspace/attachments/<id>/<file>
      └─ 模型：edit_image(prompt, images=[该路径]) → 得到 /workspace/out/<id>.png
          └─ 模型：(可选) view_image(path) 自检
              └─ 模型：prepare_chat_attachment(path) → BP 导出、校验、保存
                  └─ Reply 节点：文字＋图片附件发送；执行审计可预览
```

文生图省略导入步骤。失败、超时和审核拒绝都返回结构化错误，模型据此用文字说明，不重复刷生成。

## 3. BubblePilot 改造

### 3.1 能力声明与发现（`modules/plugins/plugin-mcp.ts`）

- **锚定工具**：指协议能力“挂靠”的那个已批准工具。BP 用它做三件事：一是能力随该工具的批准哈希一起持久化，能力变化必须重新批准；二是每次导入或导出前，先核对这个工具的批准状态；三是用它所在的 MCP 连接会话建立二进制通道。现在这个角色由 `prepare_sandbox` 固定担任，新插件用 `generate_image` 担任。
- 现状：`discover()` 只把 `imageExportVersion`、`fileExportVersion` 和 `attachmentTransferVersion` 挂到名为 `prepare_sandbox` 的工具上。
- 改为读取各协议 `experimental` 能力中的可选 `anchorTool` 字段，把版本挂到该工具上；未声明时默认使用 `prepare_sandbox`，以兼容 OpenSandbox。
- 附件协议新增可选的 `mimeTypes` 白名单。未声明时保持现状，由 BP 附件策略决定。
- 能力仍然随工具批准一起持久化。新增或变更的能力不能借由普通工具同步自动启用。

### 3.2 合格目标判定

| 文件 | 现状 | 调整 |
| --- | --- | --- |
| `plugin-image-exports.ts` `imageExportTargets` | 要求 `prepare_sandbox`（带导出版本）＋`run_command` | 声明了 `anchorTool` 的目标：锚定工具已批准且带版本即可；未声明的目标：按原规则 |
| `plugin-attachments.ts` `attachmentTargets` | 要求 `prepare_sandbox`、`run_command`、`read_file`、`write_file` 四个工具 | 同上；声明了锚定工具的目标只要求锚定工具，并返回 `mimeTypes` |
| `plugin-service.ts` `assertAttachmentAvailable` 与图片回复对应检查 | 固定核对上述四个工具的批准哈希 | 改为核对“该目标所需工具集合”，由同一个函数计算，避免分散维护 |
| `plugin-session.ts` `imageExportChannel`、`attachmentChannel` | 以 `prepare_sandbox` 作为客户端和审批锚点 | 改用目标的锚定工具；会话复用与关闭逻辑不变 |

目标列表接口（`GET /api/v1/plugins/image-export-targets` 及附件目标接口）增加 `kind`（`sandbox` 或 `generator`）和 `mimeTypes` 字段，同步更新 `contracts/openapi.yaml`。

### 3.3 内置工具与提示

- `prepare_chat_attachment`：保留 `/workspace/` 绝对路径校验。新插件对外提供虚拟工作区路径，符合同样的路径规则，因此 BP 的路径合同不改；只把描述中的“sandbox”改为中性表述。
- `import_chat_attachment`：描述改为“导入到已配置的目标”。目标声明了 `mimeTypes` 时，附件目录只把匹配的条目标记为可导入，不匹配的条目给出 `importUnavailableReason`。
- `imageReplyGuidance`、`attachmentGuidance`：去掉“bound sandbox”的硬编码，改由目标类型选择对应的指引段落。生成器类目标的指引写明：先导入再编辑、每轮一张、遇到审核拒绝不要换说法重试。
- iPhone 的 HEIC 图片：上游只接受 JPEG、PNG、WebP（已实测，HEIC 返回 400 `unsupported_file_mimetype`）。BP 现在导入附件时用 `original=true` 下载原件；送模型识图时则用 `original=false`，由 BlueBubbles 转成 JPEG。
- 改为：目标声明了 `mimeTypes`，而附件的实际格式不在名单内、属于可转换的图片（如 HEIC）时，导入改用 `original=false` 下载转换后的版本，文件名扩展名和 MIME 同步改为转换后的值，SHA-256 和大小按转换后的字节计算。沙箱目标保持下载原件。
- 不会多存一份：BP 不长期保存附件，下载只写入 `attachment-store` 的临时 `transfer-` 目录，传输完成后立即删除。原件只在网关和 iMessage 中。插件工作区里那一份随会话清理，与沙箱现状一致。

### 3.4 工作流配置与校验（`workflow-definition.ts`）

- 采用方案 B（多目标）：图片回复和附件处理支持“主目标＋可选生成器目标”，旧配置继续视为单目标。
- 路由：`import_chat_attachment` 增加可选 `target`（取值为节点已绑定的目标别名，比如 `sandbox`、`image`），缺省时使用主目标；`prepare_chat_attachment` 按返回路径所属的目标路由，各目标的路径命名空间互不重叠。工具描述只列出本节点实际绑定的目标。
- 校验：两个目标不能是同一个插件服务；生成器目标只能导入其 `mimeTypes` 内的图片；每轮仍然只发送一个附件。
- 方案 B 改动的是工作流 Schema，需要同步 `contracts/workflow.schema.json`、生成脚本和兼容测试；节点配置是 JSON，预计不需要数据库迁移，以实施时核实为准。

### 3.5 管理界面（`apps/web`）

- `ImageReplySettings.vue`：“附件输出沙箱”改为“附件输出目标”，下拉框展示目标类型和允许的文件类型；更新“请先升级沙箱插件……”等文案。
- `AttachmentHandlingSettings.vue`：“附件处理沙箱”改为“附件处理目标”，生成器类目标提示“仅接受图片”。
- `utils/plugin-tool-diagnostics.ts`：去掉“附件导入 · 沙箱”这类默认文案。
- 插件管理页：批准界面显示锚定工具和协议能力，提醒新能力需要人工批准。
- 开发预览页（`dev/attachment-preview.ts`、`dev/reply-file-preview.ts`）补充生成器目标的虚构样例。

### 3.6 预算与超时

- 单次生图、编辑可能需要数十秒。插件连接的 `callTimeoutSeconds` 上限是 180 秒，Agent 共享工具时限默认 180 秒，所以一次运行实际只能完成一到两次生成。在节点说明里写清楚，不自动放宽全局预算。
- 生成器工具结果只返回路径、尺寸和字节数等小型元数据，不把原图塞进工具结果。需要看图时走 `view_image`，复用现有的工具图片多模态链路。

## 4. 新插件 `bubblepilot-image-gen`

### 4.1 目录与发布

```text
plugins/image-gen/
├── README.md               # 部署、配置、成本与边界
├── plugin/                 # 插件包：plugin.json、mcp.json、skills/
├── server/                 # Node TS MCP 服务（Streamable HTTP），独立 package
└── deploy/                 # compose.yaml、.env.example
```

参照 `plugins/opensandbox` 的结构和 workspace 管理方式，独立构建并发布镜像，首版为 0.1.0。

### 4.2 能力声明

```json
{
  "experimental": {
    "io.bubblepilot/image-export": { "version": 1, "fileBytes": 8388608, "anchorTool": "generate_image" },
    "io.bubblepilot/attachments": {
      "version": 1, "fileBytes": 20971520, "files": 5, "totalBytes": 52428800,
      "anchorTool": "generate_image",
      "mimeTypes": ["image/png", "image/jpeg", "image/webp"]
    }
  }
}
```

如果需要发送 JPEG，同时声明 `io.bubblepilot/file-export` v1。具体数值在实施时按上游限制和 BP 校验上限（图片 8 MiB、单边 8192、1600 万像素）取较小值。

### 4.3 工具

| 工具 | 参数（草案） | 返回 |
| --- | --- | --- |
| `generate_image` | `prompt`；可选 `size`、`quality`、`background`、`output_format` | `{ path, width, height, bytes, format }` |
| `edit_image` | `prompt`、`images`（1～N 个工作区路径）；可选 `mask`、`size`、`quality` | 同上 |
| `view_image`（可选） | `path` | MCP 图片内容，供模型自检 |

- 路径都是虚拟工作区路径，比如 `/workspace/out/<id>.png`、`/workspace/attachments/<id>/<file>`，只在当前 MCP 会话内有效。
- 参数用严格 Schema，枚举值以上游文档为准；不暴露任意透传的上游参数。
- 错误使用固定代码，例如 `upstream_timeout`、`content_rejected`、`quota_exceeded`、`image_not_found`、`input_type_unsupported`，不回传上游原始错误文本。

### 4.4 会话工作区与 HTTP 通道

- 每个 MCP 会话对应一个工作区：内存或临时目录，设文件数和总字节上限，空闲超时后清理，会话关闭时立即清理；不持久化用户图片。
- 为什么要用一次性、30 秒过期的票据：附件和图片的字节流不走 MCP JSON-RPC，而是走旁路 HTTP 通道。票据只授权“当前会话里的这一个文件”（导入时还绑定 SHA-256 和大小）。一次性可以防止日志或网络中泄露的票据被重放，再导入或下载一次；30 秒只是 BP 申请票据到立即使用之间的窗口，实际间隔是毫秒级，并不限制生成或发送的次数。这是 OpenSandbox v1 协议和 BP 客户端已经实现的共同约定，新插件沿用，不另起规则。
- 实现与 OpenSandbox 语义一致的端点：
  - `POST /mcp/attachments/tickets`、`POST /mcp/attachments`：导入用户图片，校验 SHA-256、大小和 MIME；
  - `POST /mcp/image-exports/tickets`、`GET/POST /mcp/image-exports`：导出产物；如果声明了 file-export，再加对应的 `file-exports` 端点。
- 票据规则：绑定 `mcp-session-id`，一次性有效，30 秒过期，同时最多 4 张；Bearer 鉴权；错误代码沿用 BP 已识别的集合，比如 `image_path_denied`、`image_not_found`、`image_too_large`、`sandbox_busy`。
- 具体字段以 OpenSandbox 的 `attachment-http.ts`、`image-export-http.ts` 和 BP 的 `plugin-mcp.ts` 为准，实施时抽取成共享的合同测试，两个插件都跑一遍。

### 4.5 上游调用

- 配置项：`IMAGE_API_BASE_URL`（OpenAI Images 兼容中转站）、`IMAGE_API_KEY`、`IMAGE_MODEL`（默认 `gpt-image-2`）、超时、质量和尺寸上限、成本上限；都在插件配置中修改，不需要改 BP。
- 探测结果（2026-11-27，虚构提示词，低质量）：

  | 项目 | 结果 |
  | --- | --- |
  | 模型列表 | 有 `gpt-image-2`，另有 2.5、2.6 系列变体及 MiniMax 生图模型 |
  | 生成 `POST /v1/images/generations` | JSON 请求，`quality=low`、`1024x1024` 约 11 秒；返回 `data[].b64_json` PNG（约 0.85 MB）、`output_format`、`usage`（输入和输出 token） |
  | 编辑 `POST /v1/images/edits` | multipart 上传 `image`，约 12 秒，构图保持并按指令修改；输入图片计入 `image_tokens` |
  | 输入格式 | 只支持 JPEG、PNG、WebP；HEIC 立即返回 400 `unsupported_file_mimetype` |

  遮罩、多图输入、透明背景、更高质量档位的耗时和价格，在实现阶段用模拟上游加少量真实调用补测。
- 只允许访问配置的上游主机。日志不记录 prompt、图片内容或 Key，只记录耗时、尺寸、状态和用量。
- 重试：只有请求还没被上游接受时（连接失败）才重试。超时或结果未知时不自动重放，避免重复计费。
- 成本控制：每个会话的生成次数上限、每日总次数和金额估算上限，用 SQLite 或文件计数，超限返回 `quota_exceeded`。
- 产物：统一输出 PNG（必要时输出 JPEG），在插件侧先校验尺寸和字节数，再登记到工作区。

### 4.6 部署

- 独立 Compose 栈，Key 放在栈的 `.env`。
- 网络：加入 `bubblepilot_mcp`（内部网络）供 BP 访问；出网使用 `macvlan_gw11`，在 `192.168.31.64/27` 中选一个空闲地址，经 `.11` 网关访问上游。不映射宿主端口。
- macvlan 会给容器分配局域网地址，MCP 端口理论上能被局域网访问。缓解措施：HTTP 服务只监听 `bubblepilot_mcp` 网络的接口地址（启动时按网段解析，或者固定内部 IP）；所有端点仍要求 Bearer 认证。上线验收时从局域网另一台设备探测确认。
- 健康检查、只读根文件系统、非 root 用户、内存上限；工作区用 tmpfs。

## 5. 受牵连插件与环境

| 对象 | 影响 | 处理 |
| --- | --- | --- |
| OpenSandbox 适配服务与插件包 | 不声明 `anchorTool`，按默认值维持原行为；协议不变 | 不必改代码。跑共享合同测试和现有的 `opensandbox-plugin-package` 测试，做回归；可选择在后续版本显式声明 `anchorTool: "prepare_sandbox"` |
| OpenSandbox 的 Skill 指引 | 采用方案 B 后，同一节点会同时有 SVG 绘图和生图模型两种方式 | 在指引中写明分工：图表、示意图、拓扑图用沙箱绘图；照片质感的图和改图用生图插件 |
| Firecrawl | 不涉及附件和导出协议 | 无 |
| NAS 上的工作流（兰博等 6 个） | 现在绑定 OpenSandbox | 管理员显式改绑才会生效；方案 A 下改绑会失去沙箱的文件处理能力 |
| `bubblepilot_mcp` 内部网络 | 新插件加入 | 只增加成员，不影响现有连接 |

## 6. 测试与验收

**自动化（虚构数据，模拟上游，不调用真实计费接口）**

- BP：
  - 目标判定：覆盖新旧两种声明方式，OpenSandbox 的判定结果不变；
  - 审批：能力变化要求重新批准；
  - 会话通道：按锚定工具建立会话；
  - MIME 过滤；
  - 方案 B 的多目标路由，以及旧配置兼容；
  - 两种模型 API 下工具调用与结果的配对。
- 插件：
  - 票据：会话绑定、一次性、过期、并发上限；
  - 导入：哈希和大小校验；路径越界拒绝；
  - 工作区：清理；
  - 上游错误映射；限额；不重放；
  - 日志脱敏。
- 共享合同测试：同一套用例同时在 OpenSandbox 和新插件上运行。
- 照常运行：`pnpm verify`、`pnpm security:check`、各 Compose 校验，以及插件 server 自己的测试。

**联调验收（NAS）**

1. 部署插件，在管理台发现并批准工具，确认目标列表里的类型和允许格式。
2. 在测试聊天里文生图：PNG 发送成功，执行审计能预览，用量计数正确。
3. 发一张 iPhone 照片（HEIC）并要求编辑：导入、转换、编辑、发送全部成功。
4. 引用一张历史图片并要求编辑：使用的是被引用的那张图。
5. 构造审核拒绝和超时：回复如实说明，不重复生成，不重复计费。
6. 回归：用 OpenSandbox 的节点做 SVG 绘图、PDF 和表格回复、附件导入。

## 7. 实施顺序

1. **上游补测**：基本的生成和编辑已经验证，再补测遮罩、多图输入、质量档位的耗时与用量，以及错误响应的格式。
2. **BP 合同改造**（3.1～3.3、3.5）＋共享合同测试，确认 OpenSandbox 回归通过。
3. **新插件**：先接模拟上游，完成通道、工作区和工具；再接真实上游。
4. **方案 B 多目标**（如采用）：Schema、路由、界面和兼容测试。
5. **文档**：同步接口与配置契约、技术设计、部署与运维、开发与发布，以及插件 README。
6. **发布**：插件镜像和 BP 应用镜像分别发布。先部署插件，再部署 BP；最后在测试聊天中显式绑定、验收，再决定是否改绑兰博。
