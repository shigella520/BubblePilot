# BubblePilot 代码管理规范

## 1. 分支模型

BubblePilot 采用短期功能分支，不维护长期 `dev` 分支：

```text
main (protected)
  └── codex/<short-kebab-description>
          ↓ Pull Request
         main
```

分支命名示例：

```text
codex/message-ingestion
codex/workflow-engine
codex/bluebubbles-webhook
codex/fix-duplicate-replies
codex/project-docs
codex/release-v0.1.0
```

规则：

- `main` 只接受 Pull Request，禁止直接推送。
- 一个分支对应一个明确目标，尽量在数小时到数天内合并。
- 分支从最新 `main` 创建；长时间开发应拆成可独立合并的垂直切片。
- 合并后删除短期分支。
- 需要紧急修复时仍从 `main` 创建 `codex/hotfix-...`，不绕过 Review 和 CI。

## 2. Commit 消息

提交消息必须使用英文 Conventional Commit 格式：

```text
<type>(<scope>): <imperative summary>
```

允许的 `type`：

```text
feat, fix, docs, test, refactor, chore, ci, build, perf, release
```

示例：

```text
feat(webhook): handle BlueBubbles message events
fix(reply): prevent duplicate outgoing messages
docs(process): define short-lived branch workflow
test(workflow): cover retry and dead-letter states
chore(ci): validate Docker Compose configuration
```

规则：

- subject 使用英文、祈使语气，首字母不强制大写，不以句号结尾。
- 一个 Commit 只表达一个逻辑变化。
- 需要解释原因、迁移和兼容性时使用英文 body。
- 不把无关格式化、重命名和业务修改混在一起。
- PR 标题使用同样的格式；若采用 Squash Merge，PR 标题成为 `main` 的最终 Commit 消息。

## 3. Pull Request

PR 必须说明：

- 关联需求或 Issue 编号；
- 改动范围和不包含的内容；
- 数据库、配置、权限和兼容性影响；
- 测试命令和结果；
- 是否需要升级、备份或人工操作；
- 失败回滚方式。

PR 标题和代码提交使用英文；需求讨论和实现说明可以使用中文或中英双语。

## 4. Review 与合并

- Review 关注正确性、安全性、可回滚性、测试和文档同步，不只看代码风格。
- Webhook、回复发送、凭据、消息搜索和数据删除变更至少需要一次额外 Review。
- CI 未通过、存在未解决的高优先级 Review 意见或缺少迁移说明时不得合并。
- 默认采用 Squash Merge；合并后删除源分支。

## 5. 主分支与发布

- `main` 始终保持可构建、可测试状态。
- 正式版本从已验证的 `main` 提交创建，不从个人功能分支发布。
- 发布、镜像标签和迁移规则见[版本与发布规范](版本与发布规范.md)。
